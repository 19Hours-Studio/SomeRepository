Hosted LLM APIs (Anthropic, OpenAI and others) offer prompt caching. The provider stores the computed intermediate state (the attention key/value, or KV, cache) for a request's token prefix. A later request is served from that state only if its prefix is token-for-token identical, and the cached portion is billed at a discount. An edit in the middle of a prompt, an insertion, a changed tool output, or a different document order breaks the match from the first differing token onward. Everything after that point is recomputed and billed at full price. The asker wants a way to make cached context much cheaper and to reach a cache-hit rate close to 100%. This must include requests that differ from earlier ones in the middle, by insertions, tool outputs or reordered documents, and it must work without retraining or fine-tuning the model. The question does not say whether the asker runs their own serving stack or uses a third-party API, or whether the solution may sit on the client side, the server side, or both. What is the best way to do this?
A good answer: A good answer proposes one or more concrete, new or non-obvious approaches. Each must state three things:
- which request-change cases it covers: middle edit, insertion, tool output, document reordering;
- its expected hit rate and cost change, with the reasoning or a quantitative estimate;
- its effect on output quality compared with full recomputation, and how that effect could be tested.
Each approach must also say where it can run (client only, own serving stack, or provider-side) and what it costs in memory, storage and latency. It must be checked against existing prior art and say what it adds. It must state honestly which cases cannot reach about 100% under the stated constraints.
Constraints: 
- No retraining or fine-tuning of the model.
- Target hit rate close to 100% across non-identical prefixes.
- Much lower cost than current prefix caching.
- Nothing else was stated.

The final candidates with their blind reviews (data):
IDEA 1
NAME: Context-length-gated turn collapsing
MECHANISM: The anchor is that the agent stops to observe only when the expected value of seeing the result is worth one more full-context read, priced at C×0.1×p (C is the current context length, p the base input price). The threshold therefore tightens as C grows: early turns observe freely, and turns after about 20–40k tokens are folded into multi-step scripts (k=3 steps per turn). Each script filters its tool outputs down to the lines needed for the next decision, so less text enters the context and every later read shrinks. The design changes are these. Only read-only or idempotent tools are folded. A script stops early as soon as an expectation check fails. Folded batches longer than 5 minutes use the 1-hour cache TTL. On a 40-turn session the gate gives 1.48× and the gate plus 50% filtering gives 1.81×. On a 150-turn session, where reads are 75% of cost, the gate gives 2.02× and gate plus filtering gives 2.42×.
VALUE: About 2.0–2.4× cheaper per long agent task than the plain cached agent loop. That compares with 1.20× for CodeAct's measured 30% turn cut and 0.83× for observation masking once cache rewrites are paid.
BLIND REVIEW:
- MAJOR: The 150-turn gate-only figure of 2.02× breaks its own ceiling. When reads are 75% of cost and all reads are cut by k = 3, the maximum is 1/(0.25 + 0.25) = 2.00×. Turns before the 20–40k threshold are not folded, so my linear-growth model gives 1.95×. (My Python model.)
- MAJOR: The mechanism assumes every call after the threshold can be folded, but only read-only or idempotent tools qualify. At a 50% foldable share, 150 turns give 1.32× (1.50× with filtering) and 40 turns give 1.18× (1.23× with filtering). The early-stop rule cuts the effective k further. (My model with fold = 0.5.)
- MAJOR: The baseline ignores best current practice. Anthropic's Programmatic Tool Calling already folds multi-tool steps into code and filters outputs before they enter context, and parallel tool calls already batch independent reads. The comparisons at 1.20× (CodeAct) and 0.83× (observation masking) are modelled, not measured. JetBrains measured observation masking at about half the cost of the raw agent. ([Anthropic, advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use); [Complexity Trap, arXiv 2508.21433](https://arxiv.org/abs/2508.21433))
- SURVIVES: 40-turn gate-only 1.48× is close to my 1.42× at a 50% read share.
- RATIO: 1.1 | Against programmatic tool calling plus parallel calls, which already capture most of the same folding and filtering.
- KNOWN: yes | [Anthropic Programmatic Tool Calling / code execution with MCP](https://www.anthropic.com/engineering/advanced-tool-use), and CodeAct.

IDEA 2
NAME: Cost-optimal patch folding
MECHANISM: Anchor: edits become structured appended patches, and a full rewrite runs only when the patches cost more than one fresh write. Repair: the fold rule is now ski-rental, which is guaranteed to cost at most 2× what the best possible fold timing would have cost. The client folds once the patches' cumulative extra reads reach the cost of rewriting from the earliest patched position, not from the start of the document. Two triggers are new: a second edit to the same key forces a fold (depth cap 1, because the PI-LLM/DKI evidence shows accuracy on the latest value falls as updates accumulate), and folding is free on any request that would miss the cache anyway (gap longer than the TTL), since that request rewrites everything regardless. Documents are given stable section IDs when they are loaded so patches can address sections. In the model this gives 1.52× (25k document, 10 questions, 3 edits) and 2.66× (120k copilot document, 30 questions, 15 edits) against inline rewriting. The token-weighted hit rate is 96.4%, which is every reusable token; inline gets about 71%.
VALUE: Document sessions with scattered edits on hosted APIs get 1.5–2.7× lower cost per question than inline rewriting, with no more than one override per section. The gain shrinks to about 1.2–1.4× when 30% of gaps between turns exceed the cache TTL.
BLIND REVIEW:
- MAJOR: The "≤2× of optimal" ski-rental guarantee does not hold here, because the buy price changes over time. Appended conversation and earlier-positioned patches keep raising the cost of rewriting from the earliest patched position. Counterexample: a 200-token patch near the tail has B₀ = 1.25k; over 200 turns, as the context grows faster than the rent accumulates, break-even never fires. The rent paid reaches 4k, which is 3.2× OPT and unbounded as the session lengthens. (My construction under its own cost model.)
- MAJOR: Against the append-only patch chain, folding only adds cost, so its value is quality and not price. Idea 2 itself puts patch-chain cost within 4–8% of this. (Folds are extra rewrites.)
- MAJOR: The ratio depends on the pricing scheme. The 120k copilot case has an upper bound of 4.1× on Anthropic, 2.0× on OpenAI at a 0.25× read rate, and 1.5× at a 0.5× read rate, so 2.66× cannot be reached on OpenAI. (My calculation: 30 reads × 120k plus 15 edits at a mean position of 60k.)
- SURVIVES: 1.52× for the 25k case sits under my 1.83× bound. Folding for free after TTL expiry is sound. The depth-cap trigger is enforceable for in-document sections.
- RATIO: 0.95 | Against the append-only patch chain, the best current practice. It is 1.5–2.7× only against the inline-rewrite strawman.
- KNOWN: partly | Appended diff edits in coding agents (Claude Code, Aider). Ski-rental break-even folding is a textbook result. It largely duplicates Idea 2.

IDEA 3
NAME: Floating depth-1 override ledger
MECHANISM: Anchor: an edit never rewrites earlier context; it is sent as an appended patch, so the cached prefix stays byte-identical. Repair: patches no longer pile up in history. The client keeps one deduplicated ledger with a single entry per stable section or state key ("§4 now reads…", "plan.status = …"). It places the ledger after the last cache breakpoint, right after the current question, and drops it from the history it sends next turn. Each turn therefore re-pays only the ledger at 1.0× plus the reply tokens. Each key only ever has the original plus one override, so the depth-driven interference measured by PI-LLM and DKI stays at depth 1. The ledger is folded into the document when its spend exceeds one rewrite from the earliest edited position, when it passes 10% of the context, or for free on any turn where the cache has already expired. In the model, a 150k-token agent context with 8k of mutable state at the front (40 calls, 20 state edits) costs $0.0735 per request against $0.336 for inline rewriting. That is 4.6× cheaper and within 6% of the no-edit floor. A 25k-token document with 10 questions and 3 edits comes out 1.46× cheaper with the 10% cap.
VALUE: When the same state or section is edited repeatedly on a hosted API, cost per request falls 2.6–4.6× against inline rewriting, at the same cost as the patch chain coding agents already use (within 4–8%) but with override depth held at 1 instead of the chain's 3–7.
BLIND REVIEW:
- MAJOR: The baseline is a strawman. A competent operator keeps mutable state at the tail anyway, as in Manus-style todo.md recitation or append-only context. Re-sending the full 8k state each call costs about $0.093–0.101 against $0.0735, so the gain is 1.27–1.38×, not 4.6×. Against the coding-agent patch chain the idea itself says it costs the same (within 4–8%). (My calculation at Sonnet pricing ($3/M, 0.1× read, 1.25× write); [Manus context engineering](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus))
- MAJOR: "Override depth held at 1" is false in an agent loop. The 20 intermediate state values stay in the cached history inside tool outputs and assistant replies, which the design never rewrites. The interference depth the model actually sees is therefore up to 20, not 1. (20 edits across 40 calls in its own scenario.)
- MAJOR: The headline figures do not reproduce from the stated scenario. If inline costs $0.336 with front edits on 20 of 40 calls, output costs about $0.032. The no-edit floor would then be $0.077, which is above the claimed $0.0735. The implied ledger size comes out at −1.25k tokens. (My reconstruction: 150k × 0.1 × $3/M = $0.045 per read, 150k × 1.25 × $3/M = $0.5625 per rewrite.)
- MAJOR: The gain depends on the pricing scheme. OpenAI charges no write premium and discounts cache reads by 50–75%, so the same scenario falls to about 2.4× on input cost alone, before output and before the tail-state baseline. (My calculation at 0.25× read and 1.0× write: 93.75k vs 39k token-units.)
- SURVIVES: Putting the ledger after the last breakpoint keeps the prefix byte-identical. Folding for free after TTL expiry is sound.
- RATIO: 1.0 | Against the append-only patch chain, which it matches within 4–8%. It is at most about 1.3× against tail-placed state.
- KNOWN: partly | Manus todo.md recitation at the end of context, and the appended-edit practice of Claude Code and Aider.

IDEA 4
NAME: Audit-calibrated chunk KV fusion
MECHANISM: The anchor is a closed loop: 1–2% of requests are served by full recompute and also run in shadow through the reused-KV path. The results set the recompute threshold per workload against a measured answer-flip budget (the share of answers that differ from full recompute), instead of a fixed 15% recompute. The repairs are these. (1) The audit compares the whole answer by scoring it token by token under the reused KV, which catches multi-hop failures that first-token KL misses. (2) The token-selection method is pluggable, and a correcting one such as AgentKVShift is needed to get recompute down to about 10%; CacheBlend-style selection loses 47.5% F1 at 10%. (3) It stacks on top of exact-match document reordering (ContextPilot-style), and if the audit says more than 30% recompute is needed it falls back to exact matching. (4) Stored KV sits in a DRAM hot set plus a 4×NVMe array, because the node needs 24–39 GB/s of KV loads at 160 KiB/token (FP8, 70B). At 10% recompute a request costs 271 GPU-ms, against 720 for ContextPilot reordering and 1,003 for plain prefix caching. Certifying a flip rate of 2% or less at 95% confidence takes 148 clean audits, which is about 7.4k requests per calibration window.
VALUE: About 2.6× cheaper per request than the best exact-match practice (ContextPilot reordering) and about 3.7× cheaper than plain prefix caching, with a measured quality bound. It is only about 1.09× cheaper than CacheBlend at 15%, so its value is the guarantee, not the price.
BLIND REVIEW:
- FATAL: The audit can almost never certify the flip budget it promises. A zero-flip pass in 148 audits happens only 23% of the time when the true flip rate is 1%, and 48% of the time when it is 0.5%. To certify an upper bound of 2% or less with flips actually present takes about 600 audits, or 30k requests at a 2% audit rate, at a 1% true rate. At a 1.5% true rate it takes 2,150 audits, or 107k requests. That is 4–15× the stated 7.4k-request window, so low-volume workloads never get calibrated. (My Python check: (1−q)^148 and Clopper-Pearson 95% bounds. Also, 0.98^148 = 0.0503 > 0.05, so the correct zero-failure n is 149, not 148.)
- MAJOR: The "answer flip" metric is confounded by noise in full recompute itself. Two full-recompute runs of the same request differ because kernels are not batch-invariant. Long answers will differ from the reference in some token almost every time, so the flip rate needs a semantic judge, and that judge's error is not in the budget. Teacher-forced scoring under the reused KV measures likelihood shift, not flips. ([Thinking Machines](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference): temperature 0 is not deterministic on vLLM/SGLang. The "80 unique outputs in 1,000 runs" figure comes only from a secondary write-up, so I did not rely on it.)
- MAJOR: The 3.7× gain over prefix caching is larger than the gain the selected method reports for itself. AgentKVShift reports 2–3.5× prefill speedup over *no reuse*, and prefix caching is already better than no reuse. It was also tested only on 3B–32B models on a single A100, not on a 70B FP8 model. ([AgentKVShift, arXiv 2607.21604](https://arxiv.org/pdf/2607.21604): 1003/271 = 3.70×, against a self-reported 2–3.5× over no reuse.)
- MAJOR: The audit overhead is left out of the 271 GPU-ms figure, and including it erases the margin over CacheBlend. With 1–2% of requests run as full recompute plus shadow (1,003–1,600 + 271 GPU-ms), the cost becomes 284–308 GPU-ms. That is 0.96–1.04× CacheBlend at 15% (295 GPU-ms) and 2.33–2.54× ContextPilot, not 2.6×. (My recomputation: 271 + a·(F + 271), with a = 1–2% and F = 1,003–1,600.)
- MAJOR: It cannot run on Anthropic or OpenAI APIs, because these do not accept or return KV. So it does nothing for the hosted-API half of the question. (Mechanism: the provider owns the KV cache.)
- SURVIVES: 160 KiB/token (2·80·8·128 B at FP8, Llama-3-70B GQA) reproduces. 148/0.02 = 7.4k reproduces. 720/271 = 2.66 and 1003/271 = 3.70 are arithmetically correct.
- RATIO: 1.0 | Against CacheBlend at 15%, the best approximate-reuse practice, once the audit is costed (0.96–1.04×). It is about 2.4× against exact-match ContextPilot.
- KNOWN: partly | [CacheBlend/LMCache](https://blog.lmcache.ai/en/2026/04/01/accelerating-openclaw-agents-with-cacheblend/), [AgentKVShift](https://arxiv.org/pdf/2607.21604) and [ContextPilot](https://arxiv.org/pdf/2511.03475) cover the reuse mechanisms. The shadow-audit loop is standard canary practice.
