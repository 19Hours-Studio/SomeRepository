Hosted LLM APIs (Anthropic, OpenAI and others) offer prompt caching. The provider stores the computed intermediate state (the attention key/value, or KV, cache) for a request's token prefix. A later request is served from that state only if its prefix is token-for-token identical, and the cached portion is billed at a discount. An edit in the middle of a prompt, an insertion, a changed tool output, or a different document order breaks the match from the first differing token onward. Everything after that point is recomputed and billed at full price. The asker wants a way to make cached context much cheaper and to reach a cache-hit rate close to 100%. This must include requests that differ from earlier ones in the middle, by insertions, tool outputs or reordered documents, and it must work without retraining or fine-tuning the model. The question does not say whether the asker runs their own serving stack or uses a third-party API, or whether the solution may sit on the client side, the server side, or both. What is the best way to do this?

**Reading across the archetypes:**
- For a competent practitioner on a hosted API, the cache hit rate is already high in append-only agent loops (A). Their remaining cost is cache reads and writes, which a better hit rate does not change.
- The unreduced cost is in B and D, where documents are reordered or inserted and the prefix cache misses.
- On a hosted API, a client-only trick cannot beat the 0.1× read price. Only a provider-side or own-stack change can.

LESSONS:
- Reuse that is exact (prefix caching) needs identical tokens, so the discount stops at the first change. Every method that goes beyond this approximates attention, because chunk KV depends on all earlier tokens.
- The best training-free results keep about 93–98% of accuracy (APE) or still recompute about 15% of tokens (CacheBlend). Those are the 2–7% and 15% limits a new answer must beat. Nothing found reaches about 100% hits with zero quality change.
- Methods that reach 90%+ TTFT savings need fine-tuning or special tokens (Block-Attention, KVLink, possibly TurboRAG), which the constraints exclude.
- All the position-independent methods need the KV tensors, so they run on a self-hosted or provider-side stack. On a third-party API only client-side prompt layout is left (attempt 2). Providers expose no hook for approximate reuse.
- Evidence is thin: reported speedups are the authors' own, and I found no independent replication or multi-hop failure study. Any new proposal needs a quality test against full recomputation.
- Approximate reuse also changes outputs, and providers bill and promise exact semantics. That is a blocker for a provider-side rollout, which I infer and did not source.
