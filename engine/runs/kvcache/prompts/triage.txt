Which KV-cache design (storage layout, compression, eviction, quantization, offloading or reuse) can be swapped into an existing pretrained transformer LLM with no retraining and no fine-tuning, so that the same model gives the same outputs with a smaller, faster or cheaper cache? The asker wants to take any model and replace one component with another. This design should be the best across memory, speed and quality. "Best" is not defined. The answer should say which metric or workload it is best for, and where it stops working. Plausible workloads are long-context single requests, multi-user serving, multi-turn chat and prefix reuse. The asker did not give a model family, hardware, context length or serving stack. The answer may be a ranking of existing approaches, a new combination of them, or a new idea. Each claim must be checkable against published benchmarks or an experiment that can be run.
A good answer: 
- It names the criteria that define "best" (memory saved, throughput or latency, accuracy loss, calibration cost) and the workload each applies to.
- It checks "no training, any model" against published evidence: which models and architectures it was tested on, and what happens on an architecture it was not tested on.
- It gives numbers (compression ratio, accuracy change on benchmarks such as RULER, LongBench or multi-turn tasks, throughput) with sources.
- It states the conditions under which it fails, including a compression level, a task type and a model type.
- If it proposes something new, it gives a test that could show the idea is wrong.
Constraints: 
- No retraining and no fine-tuning of the model weights.
- It should be near plug-and-play and work on "any" model. See ASSUMPTIONS on whether that is possible.

Candidate answers (data):
IDEA 1
NAME: Exact tiered prefix store
MECHANISM: Hash fixed-size token blocks of each prompt and keep their FP8 key/value tensors in GPU, CPU and SSD tiers. On a later request with a matching block chain, stream those blocks back instead of recomputing them, overlapping the transfer with prefill of the unmatched suffix. Unlike CacheGen or CacheBlend, nothing is lossily encoded or approximately stitched, so outputs match the uncached run. The deciding quantity is hit rate × prefix length × (recompute time − load time), roughly 32 µs versus 2.6 µs per token for an 8B model.
VALUE: Up to about 2.5× fewer GPU-seconds on shared-prefix RAG and chat, with outputs identical to the uncached run. The hypothesis is falsified if, measured against the same stack with prefix caching off, end-to-end throughput gains less than 1.5× at a 50% hit rate.

IDEA 2
NAME: Certified-bound page skipping
MECHANISM: Each KV page stores per-channel min/max key bounds. At decode, the method computes an upper bound on each page's softmax mass and skips a page only if all skipped pages together provably carry less than ε of the attention. Otherwise it reads the full page. The closest earlier attempt is Quest, whose top-k is heuristic and gives no guarantee. This design trades some speedup for a provable error bound. The deciding quantity is the fraction of pages that can be certified as skippable at ε=1e-3 on RULER at 128K. If it is under 50%, the gain is below about 1.15× and the idea fails. It also fails on diffuse-attention tasks such as aggregation and HTML-to-TSV.
VALUE: For long single requests (A), it cuts the decode KV read with a stated error bound and no calibration.

IDEA 3
NAME: Gated per-model FP8 KV
MECHANISM: Before deployment, run a 30-minute check per model that compares FP8 KV against BF16 on RULER-128K needles and a reasoning set. Enable FP8 for each layer only where accuracy holds, and keep BF16 on sliding-window layers or any layer that fails. The closest earlier attempt is blanket FP8, which silently degraded R1-Distill and Gemma-3. This design avoids that by measuring each model before enabling FP8. The deciding quantity is the per-model accuracy delta at 128K.
VALUE: It gives a safe 2× capacity default on any dense model, but it is worth only about 1.14× in cost on long single requests and cannot reach 3×.

IDEA 4
NAME: Reversible eviction with offload
MECHANISM: Score tokens query-agnostically, in the style of KVzip, and keep about 30% on the GPU in FP8. Move the evicted blocks to CPU memory instead of deleting them. Each decode step, retrieve them page by page, as Quest does, whenever their score against the current query passes a threshold. The closest earlier attempt is permanent eviction, which fails in multi-turn chat (SCBench, FlowKV), whereas this keeps O(n) total memory. The deciding quantity is the recall rate of offloaded pages per step multiplied by the PCIe cost.
VALUE: It gives roughly 3× more concurrent users or context per GPU in multi-turn chat while staying close to FP8 accuracy, but it stalls when recall exceeds the PCIe budget.

IDEA 5
NAME: Probe-gated per-layer precision
MECHANISM: Run about 100 long prompts once with BF16 KV and once with FP8 KV, and measure per-layer attention-output error and final-logit KL divergence. Layers above a threshold stay in BF16; all others use stock FP8 kernels, so no custom datatypes are needed, unlike KVQuant. The deciding quantity is whether probe KL predicts the RULER loss.
VALUE: Turns "FP8 everywhere" into a model-checked default, with no weight changes. The hypothesis is falsified if the gated layers fail to restore RULER accuracy on Gemma-3-1B or R1-Distill.

IDEA 6
NAME: Recompute-cost-per-byte store eviction
MECHANISM: Score each stored prefix by (expected reuses × FLOPs saved) ÷ bytes held. Long prefixes score higher because attention cost is superlinear, and expected reuses decay with time since last hit. Evict the lowest scores first, instead of LRU. The closest earlier attempt is CacheBlend, which raised effective hits through approximate non-prefix reuse; this design stays exact by raising the exact hit rate. The deciding quantity is the working set against tier capacity. It is falsified if, on a replayed RAG or chat trace, the hit-weighted FLOPs saved are not at least 15% above LRU at equal capacity.
VALUE: Raises the exact-reuse hit rate h, which sets the 1/(1−0.66h) gain, without changing any model output.

IDEA 7
NAME: Bandwidth-balanced split load/recompute
MECHANISM: For each hit, choose a split point p: load KV for tokens [0,p) over the link while the GPU recomputes [p,n) from that KV as it arrives, picking p so both finish together using measured link and FLOP rates. The closest earlier attempt is Cake (2024); it is the same idea, without validation on GQA models or SSD tiers, and this design adds per-request re-estimation under batch load. The deciding quantity is the ratio of link time to compute time per token. It is falsified if TTFT is not at least 1.3× better than the better of pure-load or pure-recompute when the link is between 1 and 4 GB/s.
VALUE: Makes reuse pay off over slow network or remote storage links where pure loading only breaks even.

IDEA 8
NAME: Query-refreshed two-precision cache
MECHANISM: Keep every token in HBM at 2 bits (keys per-channel, values per-token), with an exact FP8 copy held in CPU memory. At each new query or turn, score pages by their min/max key bounds against the query, and promote the top ~10% back to FP8 in HBM in about 0.2 s. Unlike SnapKV or H2O, no token is dropped, so later turns can recover pages that the first query ignored. The deciding quantity is the RULER/SCBench gap at matched memory versus all-FP8.
VALUE: About 3× smaller decode KV at 128K context while staying safe for multi-turn use. The hypothesis is falsified if the loss exceeds 1 point versus FP8, or if it fails on long reasoning outputs where the relevant pages shift during decode.

IDEA 9
NAME: Exact-prefix tiered KV reuse
MECHANISM: Hash each KV block by its exact token prefix, as in vLLM prefix caching, and spill cold blocks to CPU or NVMe through LMCache in the model's native KV dtype. On a hit, the server streams blocks back over PCIe instead of recomputing prefill, so the outputs stay bit-identical. The closest earlier attempts are CacheBlend, which is approximate and limited to 3 models, and CacheGen, which only helps when loading beats recompute. This design avoids CacheBlend's problem because it accepts only exact prefixes. It avoids CacheGen's problem because local PCIe loads 2.6 GB in about 0.1 s against about 0.76 s of prefill (my estimate). The deciding quantity is the hit rate times the prefill saved, compared with the load time from the slowest tier used.
VALUE: In shared-prefix workloads it can cut cost up to about 2.4× with no change to outputs, but it fails on low hit rates, reordered RAG chunks and SSD-only tiers.

IDEA 10
NAME: Lossless-coded offload tier
MECHANISM: FP8 KV pages that are evicted to CPU or SSD are entropy-coded with per-layer, per-channel tables, and decoded on the GPU while they stream back, so restored caches are bit-identical. The closest earlier attempt is CacheGen, which is lossy, needs codec kernels and gains only 1.67–1.81× over 8-bit. Lossless coding avoids its accuracy risk, and it raises the prefix hit rate by fitting more prefixes into the same tier. The deciding quantity is the lossless ratio on FP8 KV. It can be falsified by measuring byte entropy on Llama-3.1-8B, Qwen and Gemma caches: below about 1.3×, or decode slower than PCIe (about 25 GB/s), and the idea is dead. It would then fail on models whose KV has near-uniform exponents.
VALUE: For RAG or chat with shared prefixes (D), it gives more cache hits per dollar of storage while keeping outputs exactly the same.

IDEA 11
NAME: Reversible top-k page reads
MECHANISM: Keep the full FP8 cache on CPU. Keep a working set of GPU pages chosen by Quest-style page min/max key bounds for each decode step, and fetch any missing pages instead of evicting them forever. The closest earlier attempts are SnapKV/H2O, which are irreversible and fail on later queries, and Quest, which keeps the whole cache on GPU so capacity is unchanged. The deciding quantity is top-k page recall per step against the PCIe bytes fetched per token. The idea is wrong if SCBench multi-turn or long-reasoning accuracy drops by more than 1 point at 10% of pages resident, or if fetch stalls exceed the 25% KV-read saving.
VALUE: It cuts long-context decode cost by up to about 1.29× and frees GPU memory without betting on future queries.

IDEA 12
NAME: FP8 tiered exact-prefix store
MECHANISM: Store the FP8 KV blocks the model already produces, hash-keyed by prefix, in GPU, then DRAM, then NVMe, and load them layer by layer, overlapped with compute. The closest earlier attempt is CacheGen; it needed a codec and won only at low bandwidth, whereas this keeps the native FP8 bytes, so a hit gives exactly what recompute would give with no decoder kernel. The deciding quantity is link bandwidth against about 1.5 GB/s for 8B (64 KB/token ÷ about 42 µs/token). It is falsified if TTFT on hits over NVMe is not at least 3× lower than vLLM's GPU-only prefix cache at a matched hit rate.
VALUE: Gives a bit-identical, any-dense-model cut of up to about 2.5× in GPU-seconds for RAG and multi-turn at hit rates near 0.9.

IDEA 13
NAME: Tiered exact-prefix KV reuse
MECHANISM: Hash each prefix block, keep hot blocks on GPU and spill cold blocks to CPU/SSD in BF16 (lossless) or FP8, and load them on a hit instead of running prefill again. The closest earlier attempt is CacheBlend/CacheGen. Both are approximate, need extra kernels, and are measured only against full recompute. Exact-prefix hits avoid that limit because outputs are unchanged. The deciding quantity is hit rate h. The gain is 1/(1−0.66·h) minus load overhead, where loading about 2.6 GB over PCIe takes about 0.1 s against about 0.76 s of prefill. The idea is wrong if, on a replayed RAG or chat trace, h is below 0.4 or loads do not overlap with compute, giving a gain under 1.3×.
VALUE: It is the only verified several-fold saving (up to 2.46× ceiling) on self-hosted RAG and multi-turn chat, with identical outputs.

IDEA 14
NAME: Layer-gated FP8 KV acceptance
MECHANISM: For each new model, run a fixed RULER and multi-turn subset at BF16 and FP8 KV. Layers whose key outlier ratio or attention-output error is largest fall back to BF16 until the quality loss is ≤1 point. The closest earlier attempts are global FP8, which degrades R1-Distill and Gemma-3, and KVQuant, which needs calibration and custom datatypes. This method uses only stock FP8 kernels and a per-layer flag. The deciding quantity is the fraction of layers that must stay BF16. The idea is wrong if that fraction exceeds 50% on the degraded models, because the capacity gain then drops below 1.33×.
VALUE: It turns "FP8 on any model" from a gamble into a checkable per-model switch.

IDEA 15
NAME: Compressed-draft, full-cache verify
MECHANISM: Decoding drafts k tokens against a 2-bit or evicted copy of the cache. The full FP8 cache, kept in HBM or CPU, then verifies all k tokens in one pass, so the final output equals the full-cache output. The closest earlier attempts are TriForce and MagicDec, which target latency and keep the full cache on the GPU. This design moves the full cache to the verify path only, and spreads its read over the accepted tokens. The deciding quantity is the mean accepted length per verify, which must exceed about 3 to beat FP8. It can be falsified on long-reasoning traces, where acceptance falls once compressed drafts drift; that is where it stops working.
VALUE: It frees GPU KV memory and reduces KV reads while keeping outputs exactly the same on any model.

ATTEMPT 1: Paged blocks plus prefix sharing (PagedAttention) | vLLM, UC Berkeley, 2023 | standard | WHY IT DID NOT SOLVE IT: It removes fragmentation (throughput 2–4× over FasterTransformer and Orca; compared systems held real token state in only about 20–38% of KV memory, via a blog's reading of the paper). It does not shrink the live cache, which still grows linearly with context and users. | [arXiv 2309.06180](https://arxiv.org/abs/2309.06180), [blog](https://ithelp.ithome.com.tw/articles/10409678)

ATTEMPT 2: FP8 KV cache | vLLM and others, 2024–26 | standard | WHY: It gives only 2× capacity and 2.6× burst throughput over BF16. Early FP8 attention kernels on Hopper had a large 128k needle regression, fixed only in a later accumulation patch. Sliding-window layers in hybrid models need FP8 skipped. So it is kernel- and version-dependent, and 2× is its ceiling. | [vLLM blog](https://vllm.ai/blog/fp8-kvcache), [TurboQuant study](https://vllm.ai/blog/turboquant)

ATTEMPT 3: KIVI, 2-bit asymmetric (keys per-channel, values per-token) | Rice, TAMU and others, ICML 2024 | standard in research, niche in production | WHY: It gives 2.6× less peak memory and 2.35–3.47× throughput at near-baseline quality. Its evidence is on Llama-2, Falcon and Mistral. The 2-bit setting is not validated for long reasoning chains (see attempts 4 and 10). | [arXiv 2402.02750](https://arxiv.org/pdf/2402.02750)

ATTEMPT 4: Low-bit quantization of other kinds (KVQuant 3-bit, TurboQuant 3–4-bit, PM-KVQ) | Berkeley 2024; vLLM 2026 test; PM-KVQ 2025 | niche | WHY: KVQuant reports <0.1 perplexity loss at 3-bit, but it needs calibration, non-uniform datatypes and custom kernels (up to 1.7× kernel speedup). vLLM measured "meaningful accuracy drops" for 3-bit TurboQuant variants on reasoning and very long context, plus worse latency and throughput. PM-KVQ's gain of up to 8% over baselines on reasoning shows naive low-bit quantization loses accuracy there. Perplexity does not predict these failures. | [KVQuant](https://neurips.cc/virtual/2024/poster/96936), [vLLM](https://vllm.ai/blog/turboquant), [PM-KVQ](https://arxiv.org/html/2505.18610v1)

ATTEMPT 5: Query-aware eviction (SnapKV, H2O, StreamingLLM) | 2023–24 | standard in research, niche in production | WHY: At 20% density SnapKV trails full attention by about 1.3 points on LongBench (Llama-3.1-8B: 47.22 vs 48.50). With a long output, SnapKV scores 0 F1 on HTML-to-TSV, and chain-of-key accuracy is below 20. H2O's headline 29× is a peak against specific OPT baselines. Eviction cannot be undone, so it is hard to deploy on arbitrary traffic. | [RefreshKV](https://arxiv.org/pdf/2411.05787), [Nexus](https://arxiv.org/pdf/2606.23961), [H2O](https://arxiv.org/abs/2306.14048v2)

ATTEMPT 9: Top-k page retrieval (Quest) | MIT and UW, ICML 2024 | niche | WHY: It keeps the full cache in memory, so capacity is unchanged. ATTEMPT 11: Non-prefix reuse (CacheBlend, in LMCache) | UChicago, Microsoft, EuroSys 2025 | niche (RAG) | WHY: It cuts TTFT 2.2–3.3× and raises throughput 2.8–5× by recomputing a small set of tokens (about 15% in vendor material). ATTEMPT 12: Compressed cache streaming and offload (CacheGen) | UChicago, 2023 | niche | WHY: It shrinks the cache 3.5–4.3× with ≤2% accuracy loss, but only helps when loading beats recompute (at 3 Gbps, TTFT is 3.1–4.7× better than sending text). ATTEMPT 16: Rankings that depend on whether the query is visible | Matched-budget audit, 2026 | cautionary | WHY: Method rankings change with query visibility at compression time, so published leaderboards do not transfer between workloads. | [arXiv 2607.11942](https://arxiv.org/pdf/2607.11942)

LESSONS:
- Only methods that keep every token (paging, FP8, prefix reuse) are safe on all workloads. Their ceiling is about 2×, plus the savings from sharing a prefix.
- Anything that drops tokens permanently depends on knowing the future query. It fails in multi-turn chat, multi-query reuse and long outputs, often at modest compression.
- The sub-4-bit and head-level methods need calibration, custom kernels, or a particular architecture. For example, DuoAttention's gain falls from 2.55× to 1.67× on GQA. This is why none of them is truly plug-and-play on any model.
- Methods are tested on few models, mostly Llama, Mistral and Qwen. None of the sources I found tested hybrid or state-space models, and SCBench only evaluated them as baselines.
- Perplexity and LongBench hide the failures. Any new answer must be tested on multi-query reuse, multi-turn runs, long reasoning and RULER, at matched budgets, with the claimed gain measured against FP8 rather than FP16.

- I = importance 0-10: how much of the asker's aim it serves if it works - for a cost question, the share of the
  delivered cost it removes, never more than the ceiling of its archetype allows;
- P = possibility 0-10: how likely it is to work at the scale it claims with known physics, given the earlier
  attempts that stopped short (a candidate that repeats one without beating its reason gets P <= 2);
- the one number that decides whether it works.
Being unusual earns nothing here; aiming at a term whose ceiling leaves no room earns a low I.
