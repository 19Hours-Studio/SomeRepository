Which architecture for compressing the LLM KV cache (the stored attention keys and values) is best if it has to be much more aggressive than FP8, which is 8 bits per value or about 2× smaller than FP16/BF16? It has to work as a drop-in replacement for the cache storage format in an existing pretrained transformer model, with no retraining, fine-tuning or architecture change, and with almost no loss of quality. The cache may be compressed along any axis: numeric precision, the number of stored tokens, channels or heads, redundancy across layers, or entropy coding. The asker calls this a "super-zip" for the KV cache. The answer should be a concrete architecture, covering what is stored, how it is encoded and decoded, and how attention reads it. It should also give the expected compression ratio and quality loss on standard long-context and reasoning benchmarks, and say what runtime cost the design adds.
A good answer: 
- It gives a specific, implementable design. Naming a family of methods is not enough.
- It states the effective bits per value or the compression ratio vs FP16, counting all metadata (scales, zero-points, indices, codebooks).
- Quality loss is stated against the FP16 cache on named benchmarks and models, for example LongBench, RULER, needle-in-a-haystack, GSM8K or MATH-style reasoning, and perplexity. "Almost no loss" is given a number, for example ≤1% relative drop.
- It is checked against the failure modes below: outlier channels in keys, RoPE, attention sinks, GQA/MLA models, long contexts, multi-turn or multi-query reuse, and reasoning-model chains of thought.
- It estimates decode and prefill latency and throughput, including dequantization or decompression cost and compatibility with FlashAttention-style fused kernels.
- It shows how it beats or complements the current state of the art (see CONTEXT), and says what is new.
- It names a cheap experiment that could falsify it.
Constraints: 
- No training, fine-tuning or distillation of the base model. The asker said "without retraining". Whether a one-time offline calibration pass on a small data sample counts is UNCLEAR.
- It must apply to any ready-made model by changing the cache storage format only.
- Compression must be far beyond FP8. This is stated as "much stronger" with no numeric target.
- Quality must drop almost not at all.

Candidate answers (data):
IDEA 1
NAME: Entropy-measured per-head bit allocation
MECHANISM: During prefill, compute each KV head's attention entropy over the prompt's own queries. Assign bit widths from that: broad heads get K2V1, middle heads K3V2, and sharp retrieval heads K4V4. Every token is kept, and the bits average about 2.1 including scales, or 7.5×. The closest earlier attempts are RazorAttention and DuoAttention. They evicted tokens in non-retrieval heads and saved only 1.67× on GQA. This design only lowers precision, which works on already-shared GQA heads and keeps multi-turn reuse safe. The deciding quantity is how stable head entropy rankings are across prompts and decode phases, measured by a Spearman rank correlation of at least 0.9.
VALUE: About 7.5× compression without calibration data, adapting per prompt to any GQA model.

IDEA 2
NAME: Rotated 3-bit fixed-codebook cache
MECHANISM: Keys and values are rotated with a fixed Hadamard matrix after RoPE. Each value is then coded with a fixed 3-bit Lloyd-Max Gaussian codebook, plus one FP8 scale per 64 values, for 3.125 bits per value or about 5.1× versus FP16. Sinks and the recent window stay in FP8, and a FlashAttention kernel dequantizes through an 8-entry lookup table in registers. The closest earlier attempt is TurboQuant, whose QJL residual added attention noise; this design drops QJL and spends that bit budget on the code itself. Anchors are KVQuant (<0.1 perplexity loss at 3 bits) and TurboQuant (neutral at 3.5 bits). The deciding quantity is the AIME accuracy gap at 32k tokens, which must be ≤1 point.
VALUE: A safe ~5× cache, against NVFP4's ~4×, with a predicted ≤1% drop on RULER and LongBench and no calibration.

IDEA 3
NAME: Hadamard-E8 lattice KV
MECHANISM: Each 128-dimensional head vector is rotated by a seeded random Hadamard transform, which spreads key outlier channels across all dimensions. The query gets the same rotation, so q·k is unchanged and keys can be stored post-RoPE. Keys use an E8 lattice code (2-bit E8P plus 1-bit residual, 3 bits per value). Values use 2-bit E8P. Each token and head also stores one FP8 scale. The first 4 sink tokens and the last 128 tokens stay in FP8. The fused FlashDecoding kernel decodes codewords from a 256-entry table in shared memory. Effective size is about 2.6 bits per value with metadata, or 6.1× smaller than FP16. On MLA models, the decoupled 64-dim RoPE part stays in FP8. The closest earlier attempt is VecInfer/MILLION, which used learned codebooks at a uniform 2 bits and broke long-CoT output. This design spends the extra bit on keys and uses a lattice code that needs no data. The deciding quantity is the AIME accuracy change at 32k tokens.
VALUE: It cuts decode KV reads about 6× (about 1.7× cheaper per token in Archetype B), with predicted loss of ≤1% on RULER-64k and LongBench and ≤2 points on AIME24. It is falsified if R1-Distill-Qwen-7B on AIME24 loses more than 2 points versus FP16, a test of about 2 GPU-hours.

IDEA 4
NAME: Cross-layer conditional entropy coding
MECHANISM: Values and pre-RoPE keys are rotated and quantized to NVFP4-grade 4-bit codes. Each token's codes at layer l are then coded losslessly with interleaved rANS, using a small count table conditioned on the same channel's code at layer l−1 and at token t−1. Pages decompress into SRAM inside the attention kernel or on transfer from a CPU or SSD tier. The closest earlier attempts are SplitZip and ZipNN, which code only BF16 exponents and reach about 25%; here the target is low-entropy indices that share the residual stream across layers. The deciding quantity is the conditional entropy H(code_l | code_{l−1}, code_{t−1}), which must be ≤2.5 bits.
VALUE: Output is bit-identical to the 4-bit format, at ≈3.0 bits per value including tables and scales, or 5.3× vs FP16. This raises prefix-cache hit rates and the number of resident requests in LMCache-style deployments. GPU rANS throughput of roughly 300 GB/s (DietGPU class) limits its speed advantage in decode-heavy HBM serving. Measuring that entropy on 1k cached sequences from Llama-3-70B and DeepSeek-V3 latents falsifies it in one hour.

IDEA 5
NAME: E8 lattice 2-bit KV
MECHANISM: Each group of 8 rotated values is coded as one 16-bit E8P lattice codeword, a fixed QuIP#-style codebook needing no calibration. One FP16 scale is stored per 128 values, giving about 2.13 bits per value, or 7.5× versus FP16. The kernel decodes from a 1 KB shared-memory table using sign flips. The closest earlier attempts are 2-bit scalar schemes such as KIVI and MILLION, which break on long chains of thought. E8's granular and shaping gain lowers distortion by about 0.2 bits' worth compared with scalar 2-bit codes. The deciding quantity is the key mean-squared error relative to scalar 3-bit codes, which must be ≤1.3×.
VALUE: If the AIME gap stays ≤2 points, it gives a near-8× drop-in cache that roughly doubles reasoning-serving batch size over NVFP4.

IDEA 6
NAME: Progressive bit-plane attention
MECHANISM: K and V are stored after a Hadamard rotation as a 2-bit base plane plus a 2-bit refinement plane, with per-group FP8 scales, for about 4.3 bits per value in total. On each decode step the kernel first scores all tokens using the base plane. It then reads refinement planes only for the top 2% of pages by score plus the sink pages, and recomputes their logits and values at 4-bit precision. The closest earlier attempts are Quest and ShadowKV, which skip pages entirely and therefore act like eviction. Here every token is still attended, and only precision varies with the query, so multi-turn reuse and question changes are safe. The deciding quantity is the attention mass covered by the top 2%, which must be at least 99% on long CoT.
VALUE: HBM reads fall to about 2.2 bits per value (about 7× fewer than FP16) at roughly NVFP4 quality. Refinement planes can be offloaded to host memory to gain capacity. The added cost is an estimated 10–15% from the two-pass kernel. It is falsified if logit KL divergence versus FP16 exceeds NVFP4's on RULER-niah-multikey.

IDEA 7
NAME: Bit-plane on-demand attention precision
MECHANISM: Keys are stored pre-RoPE and rotated, then quantized to 4-bit codes laid out as bit-planes, at 4.5 bits per value in HBM. A FlashAttention tile reads only the top 2 planes plus scales (2.5 bits per value, 6.4× fewer bytes than FP16) to score every token. It then fetches the low planes only for the ≈2% of tokens whose coarse logit could land in the top softmax mass; the 4 sink tokens and a 64-token recent window always use full planes. The closest earlier attempts are Quest and ShadowKV, which drop the tokens they do not select and so lose them on reused or multi-turn queries; here no token is ever dropped, and the tail is still read at 2 bits. The deciding quantity is the softmax mass that falls on coarse-only tokens multiplied by their value error; it must stay ≤1e-3 per head.
VALUE: About 2.6 bits read per value during decode, against NVFP4's 4.5. This should give a 1.5–1.6× decode speedup in reasoning workloads, with quality bounded by NVFP4 (≤1% drop on AIME24 and RULER-64K for R1-Distill-8B). It is falsified if a one-day PyTorch prototype misses NVFP4 accuracy on AIME24.

IDEA 8
NAME: Entropy-coded rotated tier cache
MECHANISM: For the CPU/SSD prefix tier (LMCache or HiCache), K and V are Hadamard-rotated, quantized with a uniform step at 5-bit-equivalent mean squared error, and rANS-coded per page. Entropy-constrained scalar quantization saves about 0.5 bits over Lloyd-Max at equal error on Gaussian-like rotated data, so pages land near 3.5 bits per value plus a 1% table cost. The GPU decodes pages to FP8 on load. The closest earlier attempt is SplitZip, which only coded BF16 exponents and reached about 1.33×. This design codes after rotation and quantization, where the entropy gap is large. The deciding quantity is GPU rANS decode throughput, which must exceed about 50 GB/s of output so it stays below PCIe and NVMe bandwidth.
VALUE: Each tier byte holds about 2.3× more prefixes than an FP8 tier at better-than-NVFP4 fidelity, which raises the multi-turn hit rate. It is falsified if the measured entropy of rotated KV codes on Llama-3-70B is above 4 bits per value.

IDEA 9
NAME: Progressive residual, score-guided refinement
MECHANISM: Each 16-token page stores a 2-bit rotated base code in HBM, plus a 2-bit residual in cold HBM or CPU memory, so no token is ever evicted. At decode, attention scores are computed from the base keys. For the pages holding the top ~5% of softmax mass, the residual is fetched and those pages are recomputed at 4 bits. The closest earlier attempts are KIVI-2bit, which loses about 13 AIME points because errors land on high-attention tokens, and Quest, which keeps full precision. Here only the high-attention tokens are refined. Hot storage is about 2.25 bits, roughly 7× versus FP16. The deciding quantity is the true softmax mass captured by the 2-bit top-k, which must be ≥0.99.
VALUE: About 7× HBM reduction that stays query-agnostic under multi-turn reuse and long chains of thought, cutting decode KV reads roughly 3.5× versus FP8.

IDEA 10
NAME: Bound-driven progressive bit-plane reads
MECHANISM: Rotated keys and values are stored as 6-bit codes split into bit-planes. The top 2 planes plus scales, about 2.2 bits, stay in HBM, which is 7.3×. The lower 4 planes go to CPU memory. On each decode step the kernel computes an interval for every token's score from the coarse planes. It fetches finer planes only for tokens whose upper bound could carry more than ε=10⁻³ of the attention mass, so the error is provably bounded. The closest earlier attempts are Quest and ShadowKV, which use approximate page-level selection and skip tokens. This design never skips a token; it refines precision. The deciding quantity is the fraction of tokens refined per step. It must stay below about 2% at 128k to fit in PCIe bandwidth.
VALUE: 7× HBM savings with a guaranteed attention-error bound, which makes it safe for chains of thought and reuse.

IDEA 11
NAME: Asymmetric dithered key-value codes
MECHANISM: Keys are rotated before RoPE and stored at 3 bits per channel group, plus one FP16 scale per 128 values, which is 3.125 bits. Values are stored at 2 bits per token group with dither subtracted from a shared seed, so the dither needs no stored metadata. That is 2.125 bits, for an average of about 2.65 bits, or 6.0× vs FP16. The reasoning is that score error is exponentiated, while value error averages out over the attended tokens. The closest earlier attempt is KIVI K2V2, which lost 13 points on AIME. Its 2-bit keys broke sharp attention and its error was deterministic and biased; this design keeps keys at 3 bits and makes value error unbiased. The deciding quantity is the effective number of attended tokens in retrieval heads. If it is below about 4, the value noise does not average out.
VALUE: 6× KV capacity with projected loss of ≤1% on RULER-64k and GSM8K and ≤2 points on AIME, and no calibration.

IDEA 12
NAME: Calibration-free trellis-coded KV
MECHANISM: Each rotated 256-value token-channel block is coded with a QTIP-style trellis code over a fixed Gaussian code. This is sequence-level vector quantization at 2 bits plus one FP8 scale per 64 values, 2.13 bits per value or 7.5× vs FP16. A lookup-free decode fuses into the attention tile. The closest earlier attempts are KIVI-2bit and VecInfer, whose scalar or small-codebook error collapses long chains of thought; trellis codes cut MSE about 2× over scalar quantization at equal bits.
VALUE: The deciding quantity is attention-logit MSE relative to 4-bit scalar codes, which must be ≤1.2×. If that holds, the target is ≤1% relative drop on AIME24, GSM8K, RULER-128K and NIAH for Qwen3-8B and Llama-3-70B at 7.5×, with ≈10% decode overhead. A 2-hour logit-MSE sweep falsifies it.

LESSONS:
- The ceiling for plain quantization without recovery is about 3–4 bits (4–5×). Below 3 bits, hard reasoning degrades (AIME −13 points for KIVI-2bit; GSM8K 0.90→0.72 for TurboQuant at 3 bits, secondary report). Averages like perplexity and LongBench hide this, so a new design must be tested on long-CoT.
- Eviction beyond 3–4× fails when the future query is unknown, and fails further for multi-turn reuse and reasoning chains. Any new design must be query-agnostic and must not lean on eviction for the main saving.
- Accounting must include metadata, FP16 residual windows, outlier sidecars and codebooks. Many "2-bit" claims land near 2.6× total, not 8×.
- Savings from heads and layers shrink on GQA/MLA models, which are already compressed. A drop-in design must show gains there.
- Speed claims are not credible until there is a fused FlashAttention-style kernel on real hardware: independent TurboQuant tests show +3% decode, and FP8's long-context failure came from accumulation precision, not storage.
- It is still unclear whether one-time calibration counts as "no retraining." KVQuant, Palu and DuoAttention all depend on it. A design that needs no calibration would avoid the question.
