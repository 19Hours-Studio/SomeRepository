I found four approaches. None reaches about 100% hit rate on every kind of change without some quality risk. The strongest, edit-local KV repair, has published results only, so its quality numbers still need a run on a real model; the API-only one (idea 3) can be checked on any provider. The prior art turned out to be much denser than expected. Several 2026 preprints already cover edit repair (2609.17983, 2610.17338, PatchKV) and erratum appends (2606.17107). So ideas 1–3 mostly combine published pieces, and what each adds is stated in its VALUE line. I computed the numbers with exact arithmetic and a small simulation in `cost_model.py` in the working directory; nothing was committed.

=== IDEAS ===
IDEA 1
NAME: Edit-local contiguous KV repair with fallback
MECHANISM: Runs on your own serving stack or provider-side; plain API users can't do it. It covers middle edits, insertions, deletions and changed tool outputs. Tokens before the first changed token are an ordinary exact prefix hit. Only the edited span is prefilled fresh. The old suffix after it is reused with an exact RoPE position shift (the rotation is exact; V is untouched). Then one contiguous window, from the edit to the end of its block, is recomputed, not scattered "important" tokens. At matched budget, contiguous windows beat signal-based token picking by a wide margin and run 13–21× faster than a re-prefill (2609.17983). Recomputing 2–5% of the suffix gets close to full-recompute exact match on four multi-hop QA datasets (2610.17338). Scattered selection fails on real fact edits: CacheBlend at 15% recompute scores 0.13 against 1.00 for full re-prefill (2606.17107). My addition is a stored dependency index written at prefill time: for 4 layers, each token's top-8 source blocks with their attention mass, about 96 B/token, or 0.03% of Llama-70B's 320 KiB/token. It sizes the repair window, and the request falls back to a full suffix prefill when long dependency chains point at the edited span. Arithmetic for a uniformly placed edit: prefix caching alone recomputes 50% of the context; this recomputes 1–2.5%, or 7.5% at CacheBlend's 15% rate. That is 20–50× less prefill than prefix caching, plus the cost of loading the reused KV. Test it on paired fact-edit and deletion tasks: the answer must match full recompute, and how often the fallback fires is the honest hit-rate figure.
VALUE: About 97–99% of post-edit tokens are reused instead of about 50%, so a middle edit costs about 20–50× less prefill than prefix caching. The quality claims rest on 2026 preprints and still need a run on a real model.

IDEA 2
NAME: Canonical ordering plus position-independent chunks
MECHANISM: Runs on your own stack or provider-side and covers reordered documents and RAG sets. First, sort retrieved documents and tool schemas by stable ID and popularity, so most reorders become exact prefix hits. Berkeley's relational-query reordering already shows this works, with up to 3.4× faster jobs and 32% lower cost under OpenAI and Anthropic pricing. For the rest, use a store of KV per chunk, computed once with the shared system prompt in front of it. APE showed this shared prefix removes the per-chunk attention-sink error with no training, keeping 93–98% of sequential-encoding quality. At assembly time, re-rotate positions exactly, recompute the first few tokens of each chunk (EPIC: up to 8× TTFT and 7× throughput, with negligible accuracy loss) and selectively recompute 10–15% of tokens (CacheBlend: 1–3% quality loss, 2.2–3.3× TTFT). Token hit rate is then about 85–90% for permuted sets and 100% for the canonical ones. Storage is one KV copy per chunk instead of one per prefix: 30.5 GiB per 100k tokens in BF16, about 6× less with roughly 3-bit compression. To test, compare answers under canonical, random and adversarial document orders against full recompute, which measures both the order effect and the blending error. Chunks must be isolated per tenant: HijackKV shows shared position-independent KV can be poisoned across users.
VALUE: Adding canonical ordering in front of CacheBlend/EPIC turns most reorders into lossless exact hits, so blending's 1–3% loss applies only to the remainder. Expect about 5–10× less prefill than prefix caching on RAG traffic where the document set varies.

IDEA 3
NAME: Erratum-append discipline with rebase-on-cold
MECHANISM: Client-only, so it works on any API (Anthropic: reads 0.1×, 5-minute writes 1.25×; OpenAI GPT-5: $0.125 cached vs $1.25 input). The context is append-only and serialized deterministically (sorted JSON keys, no timestamps up front, as in the Manus write-up). A middle edit or changed tool output becomes an appended erratum ("field X is now Y"), never an in-place change. Exact arithmetic for a 100k-token context: an in-place edit at a uniform position costs 6.78× a fully cached turn; an erratum costs 1.03×, a 6.6× saving per edit. Over 200 simulated turns with edits on 20% of them, total cost was 1.85× lower than in-place edits and within 4% of a context that never changes. The rule I add is to fold errata back into the context only when the cache is being rewritten anyway (TTL expiry, compaction), which costs nothing extra. A ski-rental rule never triggered in the simulation for 200-token errata. Quality caveat: the model uses the erratum reliably mainly with chain-of-thought (2606.17107). Without it, test erratum vs in-place on your own tasks and compare to a fresh prompt. That paper reports a 98.5% hit rate in an online vLLM benchmark.
VALUE: Hit rate near 100% and about 1.85× lower input cost for edit-heavy agents on any API. The floor is the provider's read price (0.1×); nothing client-side can go below it.

IDEA 4
NAME: TTL-aware keepalive and write-tier choice
MECHANISM: Client-only, and covers misses caused by expiry, not by changed content. Reads refresh Anthropic's 5-minute TTL for free. On a 100k-token context, a ping every 4 minutes costs 0.1N each; the 1-hour tier costs an extra 0.75N once; letting the cache expire costs 1.15N to rewrite. Keepalive is cheapest for idle gaps under about 30 minutes (70k vs 75k units at 30 minutes), the 1-hour tier for gaps of about 30–60 minutes, and expiry beyond that. Quality is unaffected because reuse stays exact. Latency is unchanged; the extra traffic is tiny pings. Gemini's explicit caching instead charges storage ($4.50 per million tokens per hour on Pro), so the same rule has to compare that hourly fee against the rewrite cost. Check your provider's terms before running keepalive pings.
VALUE: For bursty agent or chat sessions this removes the TTL miss term, up to 1.15N per idle gap, without touching the prompt.

Cases that can't reach about 100% under these constraints:
- **Plain API users:** ideas 1 and 2 aren't available, and cost can't go below the provider's read price.
- **Semantic middle edits that later text depends on:** these need recompute in proportion to how long the dependency chain is, so the fallback rate decides the real hit rate.
- **Quality equal to full recomputation:** nobody gets this for free without training. Attuner closes the gap but needs adapter training, which is excluded here.
- **Output tokens:** caching doesn't change them. Manus reports a 100:1 input-to-output ratio, but traffic with more output is limited by output cost.
- **Model-dependent numbers:** every quality figure above, plus the fallback rate in idea 1, needs a run on a real model, which wasn't possible here because Hugging Face is blocked.
