QUESTION: Hosted LLM APIs (Anthropic, OpenAI and others) offer prompt caching. The provider stores the computed intermediate state (the attention key/value, or KV, cache) for a request's token prefix. A later request is served from that state only if its prefix is token-for-token identical, and the cached portion is billed at a discount. An edit in the middle of a prompt, an insertion, a changed tool output, or a different document order breaks the match from the first differing token onward. Everything after that point is recomputed and billed at full price. The asker wants a way to make cached context much cheaper and to reach a cache-hit rate close to 100%. This must include requests that differ from earlier ones in the middle, by insertions, tool outputs or reordered documents, and it must work without retraining or fine-tuning the model. The question does not say whether the asker runs their own serving stack or uses a third-party API, or whether the solution may sit on the client side, the server side, or both. THE 10 IDEAS:
IDEA 1
NAME: Return-hazard priced keep-alive
MECHANISM: The client logs the gaps between turns per user and per tool, including long test runs. From this it fits a survival curve, S(t) = the probability the user has not yet returned after t minutes. Just before a 5-minute expiry, it sends a 1-output-token read of the whole prefix only if the expected cost of rewriting (P(return soon) × 1.25 × prefix) exceeds 0.1 × prefix. It uses the 1-hour TTL only on the stable header when parallel sub-agents will read it. The closest prior art is fixed keep-alive scripts and the blanket 1-hour TTL. Those either ping dead sessions forever or pay +0.75× on every write, whereas this rule prices each gap. Deciding quantity: the share f of write tokens that are rewrites after expiry. If f = 0.4, the saving is about 15% of the bill (about 1.18×). It runs client-only and adds roughly zero latency; time-to-first-token after an idle gap also improves.
VALUE: It removes rewrites after expiry and during tool waits for about 0.1× per window, without changing output.
DECIDING QUANTITY: f, the share of cache-write tokens that are rewrites after the cache expires (the only cost this idea can remove)

IDEA 2
NAME: Append-only journal with cost-optimal compaction
MECHANISM: This runs on the client only, works with any plain API, and is the only approach here that is exact. Never change earlier tokens. A middle edit or insertion becomes a short correction appended at the end ("§3.2 now reads …"). Tool outputs are never cut back in place. Documents go in a fixed order, sorted by content hash, and the relevance ranking is given in a short note at the end. Rewriting from the earliest edit point (compaction) happens only when a ski-rental rule says so: compact once the 0.1x re-read spend on accumulated corrections reaches (1.25−0.1)·(N−p_min). This rule is guaranteed to cost at most 2x the best possible schedule. My exact arithmetic for a 100k context with a 400-token edit at 30k: rewriting in place costs 90,500 base-token units, appending costs 10,500, so appending is 8.6x cheaper this turn and stays cheaper for 2,000 later turns. For idle gaps longer than the 5-minute TTL, a 1-token "keep-alive" request costs 0.1N against 1.25N for rewriting after a miss. That pays for up to 12.5 pings (about 62 minutes) if the user is sure to return, or 5.8 pings if the chance is 50%. A 1-hour write costs the same as 7.5 pings. On the cost side, there is no extra memory and no extra latency. The appended text adds a few hundred tokens per edit, re-read at 0.1x.
VALUE: Every request type becomes a pure prefix extension, so the hit rate equals 1 − (new tokens / total). That is typically 94–98% per agent turn. Against a client that edits in place, a single missed 10% of old context per turn adds 69% to the bill (35% at 5%). Quality risk: the model now sees the stale text plus a correction rather than a clean edit. Test it on your own evals (SWE-bench-style pass rate) and measure how often stale facts leak into answers, comparing journal against rewrite. This needs a real-model run.
DECIDING QUANTITY: Hit-rate gain over best practice, which is already append-only for agents (ledger A) and already uses canonical chunk order for RAG (ledger B)

IDEA 3
NAME: Attention at the KV store
MECHANISM: On each agent turn, only the new suffix is prefilled. The suffix's queries go to the node that already holds the session's prefix KV, and that node returns partial attention outputs with log-sum-exp values. These merge exactly with local attention over the suffix, so the KV never moves and the output matches full recomputation bit-for-bit up to floating-point order. Closest earlier work: Lamina (2024) offloads decode attention only; this applies the same split to suffix prefill. The deciding quantity is traffic, n·Hq/(L·Hkv) = 8n/L. It wins whenever the n new tokens are fewer than L/8, for example 2k new tokens over a 100k context gives about 6× less traffic than a BF16 fetch. Costs: 80 per-layer round trips per turn, and compute on the store node. It runs on your own stack or provider-side.
VALUE: Hits on 100k+ contexts become cheap from any replica without moving the KV. This lowers the provider's cost of cache reads (42% of the bill), but it does nothing for middle edits.
DECIDING QUANTITY: Share of the total cost that comes from moving KV (the only thing this idea removes)

IDEA 4
NAME: Canonical ordering plus position-independent chunks
MECHANISM: Runs on your own stack or provider-side and covers reordered documents and RAG sets. First, sort retrieved documents and tool schemas by stable ID and popularity, so most reorders become exact prefix hits. Berkeley's relational-query reordering already shows this works, with up to 3.4× faster jobs and 32% lower cost under OpenAI and Anthropic pricing. For the rest, use a store of KV per chunk, computed once with the shared system prompt in front of it. APE showed this shared prefix removes the per-chunk attention-sink error with no training, keeping 93–98% of sequential-encoding quality. At assembly time, re-rotate positions exactly, recompute the first few tokens of each chunk (EPIC: up to 8× TTFT and 7× throughput, with negligible accuracy loss) and selectively recompute 10–15% of tokens (CacheBlend: 1–3% quality loss, 2.2–3.3× TTFT). Token hit rate is then about 85–90% for permuted sets and 100% for the canonical ones. Storage is one KV copy per chunk instead of one per prefix: 30.5 GiB per 100k tokens in BF16, about 6× less with roughly 3-bit compression. To test, compare answers under canonical, random and adversarial document orders against full recompute, which measures both the order effect and the blending error. Chunks must be isolated per tenant: HijackKV shows shared position-independent KV can be poisoned across users.
VALUE: Adding canonical ordering in front of CacheBlend/EPIC turns most reorders into lossless exact hits, so blending's 1–3% loss applies only to the remainder. Expect about 5–10× less prefill than prefix caching on RAG traffic where the document set varies.
DECIDING QUANTITY: Quality loss against full recomputation when 10–15% of tokens are recomputed, on long or multi-hop RAG

IDEA 5
NAME: Erratum-append discipline with rebase-on-cold
MECHANISM: Client-only, so it works on any API (Anthropic: reads 0.1×, 5-minute writes 1.25×; OpenAI GPT-5: $0.125 cached vs $1.25 input). The context is append-only and serialized deterministically (sorted JSON keys, no timestamps up front, as in the Manus write-up). A middle edit or changed tool output becomes an appended erratum ("field X is now Y"), never an in-place change. Exact arithmetic for a 100k-token context: an in-place edit at a uniform position costs 6.78× a fully cached turn; an erratum costs 1.03×, a 6.6× saving per edit. Over 200 simulated turns with edits on 20% of them, total cost was 1.85× lower than in-place edits and within 4% of a context that never changes. The rule I add is to fold errata back into the context only when the cache is being rewritten anyway (TTL expiry, compaction), which costs nothing extra. A ski-rental rule never triggered in the simulation for 200-token errata. Quality caveat: the model uses the erratum reliably mainly with chain-of-thought (2606.17107). Without it, test erratum vs in-place on your own tasks and compare to a fresh prompt. That paper reports a 98.5% hit rate in an online vLLM benchmark.
VALUE: Hit rate near 100% and about 1.85× lower input cost for edit-heavy agents on any API. The floor is the provider's read price (0.1×); nothing client-side can go below it.
DECIDING QUANTITY: share of the best-practice agent bill caused by in-place middle edits, which is the only thing errata can remove

IDEA 6
NAME: Content-addressed position-independent KV with gated repair
MECHANISM: This runs on your own serving stack or on the provider side. Split token streams at content-defined boundaries: a rolling hash over token IDs plus message and tool delimiters. A re-sent span (a reordered document, a re-read file, a moved tool output, the text after an insertion) is then found at any offset with an O(1) hash lookup. Store keys before the positional rotation is applied, so reusing them at a new position is free inside the attention kernel. Repair in layers: recompute the first ~32 tokens of each chunk to remove the false attention-sink effect (EPIC), the top-r tokens by key deviation (CacheBlend), and a 16-token window after each splice point. Add a quality gate: on ε≈1% of traffic, run a full recompute in shadow, compare the next-token distributions (KL) on the first 32 output tokens, and adjust r per chunk type. Fall back to exact recompute when the gate fails. My model for 8×512-token chunks with a 1k system prompt in a new order on an 8B model, against full recompute: EPIC-only repair needs 8.4% of full compute, r=15% needs 15.6%, the full stack needs 23.2%, and r=30% for multi-hop needs 27.9%. Prefix caching here needs ~83% of full compute, because only the system prompt hits. Memory: 128 KiB of KV per token at 8B (320 KiB at 70B, so 328 GB per 1M tokens). Loading 4,096 reused tokens takes 10.7 ms over PCIe5 or 77 ms from NVMe, against ~152 ms for full prefill. The shadow check adds ε of full prefill.
VALUE: On reordered or re-positioned content, compute drops 3–10x against prefix caching, and token reuse rises from 19% to 74–92%. Prior art covers most of the parts: CacheBlend, EPIC, Cache-Craft, KVShare, SemShareKV, and LMCache's CacheBlend for agents. What this adds is offset-independent lookup plus a quality SLO with exact fallback. Quality is model-dependent. KVShareArena finds that repairs recover only half to two-thirds of the gap on multi-source questions, and that unrepaired caches can be worse than no cache. So "≈100% hit at full quality" is not reachable for multi-hop work. The deciding test is KL/F1 against full recompute on 2WikiMQA, MuSiQue and agent replays (needs a real model).
DECIDING QUANTITY: fraction of the quality gap (no cache vs full recomputation) recovered by partial-recompute repair on multi-source queries; "≈100% hit at full quality" needs about 0.95 or more

IDEA 7
NAME: Diff-encoded repeated tool outputs
MECHANISM: The client hashes every tool output it has already placed in context. When a file or command result is requested again, it appends only "unchanged since turn 12" or a unified diff, never a second full copy. This shrinks the genuinely new tokens that pay the 1.25x write charge. The closest prior art is the file-unchanged notices in some agents. Those cover only identical re-reads; this also handles changed outputs as deltas, so a changed tool output costs the size of its diff, not its full size. The deciding quantity is the share of written tokens that duplicate content already in context, measurable from agent traces. Quality should be tested by SWE-bench and Terminal-Bench pass rate and by error rates when applying diffs.
VALUE: Directly shrinks Archetype A's largest term, cache write at 47% of the agent bill, when re-reads dominate the written tokens.
DECIDING QUANTITY: share of written plus re-read tokens that duplicate content already in context

IDEA 8
NAME: Cut the re-read bill, not misses
MECHANISM: This runs on your own stack or provider-side. Once hits are near 100%, re-reading cached context dominates. In my model of a 50-turn agent (20k base context, +2k tokens per turn, 300 output tokens per turn), cached reads at 0.1x are 60.5% of the bill, writes 26.3% and output 13.2%. Re-read cost grows with the square of the number of turns. So hold cached KV pages in CPU/SSD and fetch only the top-K pages per query (Quest-style min/max key bounds per page, no training) for decode and for attention from new tokens. With a 2–4k token budget, that reads 6.4–12.8% of the dense KV at 32k context and 1.6–3.2% at 128k. Page metadata adds about 6% of the KV size. Quest reports up to 7.03x faster self-attention and 2.23x lower latency, with negligible accuracy loss.
VALUE: This targets the largest remaining cost line at a near-100% hit rate. It could plausibly lower the per-token cost of cached reads by about 2–5x end to end. IDEA 9
NAME: Write-anchor audit and skip
MECHANISM: The client scans usage logs for write spikes larger than half the context. These are full rewrites caused by a turn adding more than about 20 blocks (for example, parallel tool results) past the provider's lookback limit. It fixes them by always keeping a second breakpoint at the end of the previous request and by merging tool-result blocks. It also places tokens that will never be read again after the last breakpoint, so they are billed at 1.0× instead of 1.25×. Examples are a sub-agent's final call and outputs that are about to be cleared. The closest prior art is Anthropic's breakpoint guidance, which states the lookback rule but does not detect or price the misses. Deciding quantity: the miss rate per turn. At 5k new tokens per turn, one 100k-token miss every 50 turns adds 40% to the write term.
VALUE: It removes hidden full-prefix rewrites, which can be a large share of the 47% write term.
DECIDING QUANTITY: Share of the cache-write term that comes from hidden lookback-miss rewrites (the part this idea can remove)

IDEA 10
NAME: Edit-local contiguous KV repair with fallback
MECHANISM: Runs on your own serving stack or provider-side; plain API users can't do it. It covers middle edits, insertions, deletions and changed tool outputs. Tokens before the first changed token are an ordinary exact prefix hit. Only the edited span is prefilled fresh. The old suffix after it is reused with an exact RoPE position shift (the rotation is exact; V is untouched). Then one contiguous window, from the edit to the end of its block, is recomputed, not scattered "important" tokens. At matched budget, contiguous windows beat signal-based token picking by a wide margin and run 13–21× faster than a re-prefill (2609.17983). Recomputing 2–5% of the suffix gets close to full-recompute exact match on four multi-hop QA datasets (2610.17338). Scattered selection fails on real fact edits: CacheBlend at 15% recompute scores 0.13 against 1.00 for full re-prefill (2606.17107). My addition is a stored dependency index written at prefill time: for 4 layers, each token's top-8 source blocks with their attention mass, about 96 B/token, or 0.03% of Llama-70B's 320 KiB/token. It sizes the repair window, and the request falls back to a full suffix prefill when long dependency chains point at the edited span. Arithmetic for a uniformly placed edit: prefix caching alone recomputes 50% of the context; this recomputes 1–2.5%, or 7.5% at CacheBlend's 15% rate. That is 20–50× less prefill than prefix caching, plus the cost of loading the reused KV. Test it on paired fact-edit and deletion tasks: the answer must match full recompute, and how often the fallback fires is the honest hit-rate figure.
VALUE: About 97–99% of post-edit tokens are reused instead of about 50%, so a middle edit costs about 20–50× less prefill than prefix caching. The quality claims rest on 2026 preprints and still need a run on a real model.
DECIDING QUANTITY: Share of real edits whose quality matches full recompute without falling back (the dependent text must sit next to the edit)
