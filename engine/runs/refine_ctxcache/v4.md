# How to make cached context much cheaper, with hits near 100%

All numbers come from `calc.py` in this directory. `python3 -I calc.py` takes about 2 minutes and needs only the standard library; its output is in `calc_out.txt`. The SWE-agent trajectories are in `traces/`. `cachediff.py` finds where one request breaks the cache relative to the one before it, and `examples/` holds the test pairs. Nothing was committed. No model weights could be downloaded (huggingface.co, ModelScope and Ollama are all blocked), so **every quality claim below is either a published result or an untested hypothesis.**

**What's new in this version:**
- **§K, parallel fan-out:** concurrent requests on the same prefix all miss. Sending one warm-up request first makes the prefix 5.8× cheaper at 10 parallel requests.
- **§L, batch plus caching:** the batch discount stacks with caching, which halves the whole bill. It only beats interactive use if at least about 81% of requests inside the batch hit the cache (for the workload modelled).
- **§M, clearing period for API users:** clearing old tool results every ~8 turns, rather than every turn or never, brings a 200-turn agent's total bill to **0.43×**. A square-root rule predicts the best period. This is how to set Anthropic's `clear_at_least`.

## Short answer, by who you are

| You are | What gets you to ~100% hits and a lower bill | Exact? |
|---|---|---|
| **API user** | Idea 1: append-only layout, volatile blocks last, errata instead of edits, breakpoints and TTL, one warm-up request before fan-out, clearing on the square-root schedule, batch where possible. `cachediff.py` finds each break. | Yes, except clearing, which drops content on purpose |
| **Self-hosting** | Idea 1, plus a chat template that doesn't rewrite history (or send token IDs), Idea 2 (splice KV in place) and Idea 4 (retention priced against recompute cost) | Ideas 1 and 4 exact, Idea 2 approximate |
| **Provider** | All of the above, plus Idea 3 (a segment cache with a gate calibrated by shadow sampling), sold as a separate, cheaper "approximate hit" | Idea 3 approximate, gated |

**Key fact 1.** No exact method can reuse KV after a token that changed in place. Every server-side method for real middle changes is approximate. It must be checked against full recomputation and priced separately. "Near 100% and exact" therefore requires the client to stop changing content in place.

**Key fact 2.** At 100% hits the input bill is mostly cached reads plus writes. "Much cheaper" therefore also means *reading fewer tokens* (§M, Idea 2) and *paying less per token* (TTL, batch). A higher hit rate cannot deliver either.

## 0. What the bill is made of at 100% hits (`calc.py` §A, G, K, L)

The model is a 50-turn agent:
- a 10k-token system prompt, plus 2k tokens of tool output and 300 output tokens per turn;
- Anthropic-style multipliers: write 1.25×, read 0.1×, output 5× the base input price;
- each turn's output is written to the cache on the next turn.

**The bill splits into reads 59%, writes 28%, output 13%.** None of these shrink when the hit rate rises.

**Measure the hit rate from usage fields:**
- Anthropic: `cache_read_input_tokens / (cache_read + cache_creation + input_tokens)`.
- OpenAI: `cached_tokens / prompt_tokens`. From GPT-5.6 on, OpenAI also reports `cache_write_tokens` and bills writes at 1.25×.

**Levers that don't depend on layout:**

| Lever | Effect | Condition |
|---|---|---|
| **TTL (§G)** | A context reused N times at 6–60-minute gaps costs 1.25·(N+1) per token with a 5-minute TTL (7.5× at N=5), but 2 + 0.1·N with a 1-hour TTL (2.5×) | Gaps longer than 5 minutes |
| **Warm-up before fan-out (§K)** | Anthropic says a cache entry becomes available only after the first response begins. Concurrent requests on a shared prefix P therefore all miss and all write. Sending one request first (`max_tokens=1` is enough) and then the rest makes P cheaper by 1.9× at N=2, **5.8× at N=10** and 10.2× at N=50 | Costs one extra time-to-first-token |
| **Batch plus caching (§L)** | Anthropic's 50% batch discount stacks with cache multipliers, so a cached read costs 0.05× base. Hits inside a batch are best-effort, so send one synchronous warm-up with a 1-hour TTL first. With a 20k prefix, 1,000 requests and 500 output tokens each, batch costs **0.56×** interactive at 98% in-batch hits, but 1.28× at 70% and 2.30× at 30%. **Break-even is 81% in-batch hits.** | Workload can wait; measure in-batch hits from the usage fields first |
| **Routing** | OpenAI asks you to keep each `prompt_cache_key` to about 15 requests per minute. Above that, requests miss even with an identical prefix. Split traffic over ⌈rate/15⌉ keys with a stable mapping | OpenAI |
| **Minimum length and granularity** | Prompts below the minimum are never cached: 1,024 tokens on most models, and the docs list 4,096 for some (Opus 4.5/4.6, Haiku 4.5). OpenAI matches in 128-token steps. Short prompts can never reach 100% | — |

## Idea 1: Cache-stable prompt layout (client only, exact)

**Where it runs and what it costs:** any API. No extra memory or storage, and latency is the same or lower.

**1a. Ordering rule.** Assume each block i (size sᵢ) changes independently with probability pᵢ per request.
- An exchange argument on neighbouring blocks shows the best order sorts blocks by **pᵢ / ((1−pᵢ)·sᵢ), ascending**. That is the odds of a change per token, not the probability.
- Brute force over 3,000 random 6-block layouts (§C): this rule was optimal in all 3,000.
- The plain p/s rule was suboptimal in 59% of them, by a median of 1% and at most 17%.

**1b. Volatile tail, diff-only re-sending.**
- Put the to-do list, memory and current state after the conversation.
- Re-send a block only when it changed, as a diff.
- Place the last cache breakpoint *before* the tail. Tail tokens are then billed as plain input (1.0×) rather than as a write (1.25×). They are never read back, so this saves 20% of the tail's cost (§J).

**1c. Append-only errata and normalization.**
- Turn a middle edit, an insertion or a changed tool output into a short note at the end, such as `[supersedes tool_result #17]: …`.
- Normalize timestamps, UUIDs, JSON key order and unordered listings.
- Serialize document sets in a canonical order.

**1d. Folding errata back in (ski rental).** Rewrite the errata into place after T* = (1.15·S − 1.25·e)/(0.1·e) turns, where e is the erratum size and S is the number of tokens after the edit point.
- S = 50k, e = 500 gives 1,138 turns. S = 10k, e = 2k gives 45 turns. If S ≤ e, rewrite now.
- Rewriting at T* costs at most 2× the best schedule chosen in hindsight.

**1e. Clearing old content on a square-root schedule (§M, new).** Errata stop the rewrites, but reads still grow with context length. That is the 59% share. Dropping old tool results cuts reads, and each clear re-writes everything after the first cleared block.

Simulated agent: 200 turns, 10k system prompt, 2k tool output and 300 output tokens per turn. Tool results older than 3 turns become 20-token placeholders.

| Clear every | 1 turn | 5 | **8 (best)** | 10 | 40 | 100 | never |
|---|---|---|---|---|---|---|---|
| Total bill | 0.56× | 0.43× | **0.43×** | 0.43× | 0.51× | 0.69× | 1.00× |

- This assumes the prefix up to the clear point stays cached, as in vLLM or OpenAI-style block caching.
- If only the system prompt survives (Anthropic without a breakpoint at the clear point), the best period becomes 20 turns at 0.49×.
- **Rule:** T* ≈ √(2·1.25·K / (0.1·g)). Here K is the number of tokens re-written per clear (the kept window, plus the system prompt if nothing anchors the cache there), and g is the number of clearable tokens added per turn. It predicts 9 and 15 turns against the simulated 8 and 20.
- On Anthropic this means setting `clear_at_least` to about T*·g. Anthropic's context-editing docs say clearing invalidates the cached prefix and recommend clearing "enough tokens to make the cache invalidation worthwhile".
- **Regime caveat:** in §D's short real SWE-agent sessions (median observation 65 tokens), eliding on every step cost 1.79× at 30 steps. Clearing pays off only when observations are large and sessions long. Compute T* from your own g and K.
- **Quality:** this drops information on purpose. Test task success (for example SWE-bench resolve rate) against keeping everything, across a range of T.

**1f. Failure modes that break the cache without any edit you meant to make.**
- **Anthropic's 20-block lookback.** Hits are looked for only about 20 content blocks back from each breakpoint. Take a 200-block conversation with a single breakpoint at the end. An edit at block 150 loses *everything*, including the 13k system prompt and tools (§J). Add explicit breakpoints (up to 4): after the tools and system prompt, after the documents, and before the clear point from 1e.
- **Concurrent fan-out.** See §K above. This also covers subagents started in parallel from one parent context.
- **Templates that rewrite history.** Qwen3-style templates drop earlier reasoning when a new user message arrives, and gpt-oss drops analysis once a final answer exists. Each new query then re-renders the previous query from its first assistant turn.
  - In §H (10 queries; 300 reasoning, 100 action and 1,000 observation tokens per step), the hit rate falls from 97.7% to 94.7% at 5 tool steps per query. Per-token input cost becomes **1.27×**, or 1.10× at 20 steps.
  - xAI's docs name dropped `reasoning_content` as the top cause of misses.
  - Fixes on your own stack: render with reasoning kept (if quality holds), send token IDs instead of text (which also avoids re-tokenization drift), or strip reasoning with an in-place splice (Idea 2).
- **Re-serialization.** Key order, tool-schema order and changing timestamps are common causes.

**1g. Tool: `cachediff.py prev.json next.json`.** Give it two consecutive request bodies (Anthropic or OpenAI format). It reports:
- the first block that differs;
- a likely cause: timestamps only, IDs only, key order, reordered lines, reasoning removed, or a real edit;
- how many unchanged tokens after that point get recomputed, and the resulting cost multiplier;
- a warning when the 20-block lookback will lose the prefix.

On `examples/`, a one-character change to a tool output at message 4 of 61 leaves an 11% cacheable prefix and costs 11.2× a full hit. A tool schema with reordered keys gives 0% and costs 12.5×. Token counts are chars/4 estimates.

**Cases and hit rate (§C).** The agent layout is a 3k system prompt, 8k of tools, 2k of memory changing on 10% of turns, a 500-token to-do list changing on 50% of turns, 20k of documents changing on 2% of turns, a 40k conversation, and 1k new tokens per turn.

| Layout | Token hit rate |
|---|---|
| Authoring order | 47.1% |
| Best order, conversation last | 67.4% |
| Volatile tail after the conversation | 93.7% |
| + document changes as errata | 95.3% |
| + tail re-sent only when changed | **98.0%** |

- A middle edit, insertion or changed tool output costs only the erratum: about 99.3% hits on that turn for a 500-token erratum in a 74k prompt.
- Reordering a document set that was already seen costs nothing (100%), because canonical order makes the reorder invisible.
- **RAG with a different document set per query (§E).** 2,000 documents of 500 tokens, 5 per query, Zipf popularity with s = 0.8–1.2.
  - Total hit rate: relevance order 55–63%, hash order 57–68%, **popularity order 63–77%**.
  - Document tokens only: 20–33% for relevance order versus 34–60% for popularity order.
  - A greedy radix-tree walk (CacheWeaver/RAGBoost style) adds only 0–0.4 points over static popularity order under i.i.d. Zipf. It should matter more when popularity drifts or topics correlate, which was not modelled.

**Quality.** The KV is exactly what the model computes for the prompt it receives. The risks are in what the prompt says:
- stale text stays next to its correction;
- popularity order differs from relevance order ("lost in the middle");
- reasoning kept in history is out of distribution for templates trained to strip it.

Tests, as A/B comparisons on a real model:
- a needle test where a superseded fact sits next to its erratum;
- SWE-bench resolve rate with errata versus in-place edits, and with reasoning kept versus stripped;
- RAG QA under relevance versus popularity order, with and without an order hint.

**Prior art and what this adds.**
- Already known:
  - Manus and Anthropic advise append-only context with stable content first.
  - *Don't Break the Cache* measures 41–80% cost cuts from keeping dynamic tool results out of the cached prefix.
  - RAGCache, RAGBoost/ContextPilot and CacheWeaver reorder documents for reuse.
  - Anthropic documents the concurrency rule and `clear_at_least`.
  - xAI and practitioner write-ups describe the reasoning-stripping trap.
- New here:
  - the odds/size ordering rule, with a counterexample to p/s;
  - the diff-only tail placed after the last breakpoint;
  - the ski-rental threshold for folding errata back in;
  - the square-root clearing period (how to set `clear_at_least`);
  - the fan-out and batch break-evens;
  - quantified costs of the lookback and template traps;
  - the break-diagnosis tool;
  - the finding that static popularity order captures nearly all of the greedy walk's gain under i.i.d. Zipf.

## Idea 2: Delete and splice KV in place (own stack or provider, approximate)

**Mechanism.** An operation `edit_span(range, replacement)`:
1. Drop the span's paged KV blocks.
2. Re-rotate the RoPE keys after the span, or leave a gap in position IDs.
3. Prefill only the replacement.
4. On sampled requests, compare against exact recomputation of the suffix (the gate from Idea 3).

**Cost.** No extra memory, since freed blocks return to the pool. Re-rotation is O(suffix) element-wise work. Compared with 1e, it removes the rewrite cost entirely, so clearing can happen on every step.

**Cases.** Clearing old tool results, replacing a tool output, and stripping earlier reasoning (1f) without re-rendering. The hit rate for a replacement is remaining / (remaining + replacement).

**Trace replay (§D).** Real step sizes from 3 small SWE-agent trajectories (41 messages, chars/4), resampled into 30- and 80-step sessions, keeping the last 5 observations. Treat this as illustrative only.

| Policy | Hit, 30 steps | Input cost, 30 steps | Hit, 80 steps | Input cost, 80 steps |
|---|---|---|---|---|
| Append-only | 94.4% | 1.00× | 97.8% | 1.00× |
| Client elision every step | 69.8% | **1.79×** | 80.1% | 1.30× |
| Client elision every 15 steps | 90.5% | 1.05× | 94.4% | 0.77× |
| **Server splice** | 91.8% | **0.82×** | 95.5% | **0.62×** |

The splice keeps the saving from deletion without paying for the rewrite. Its hit rate is slightly lower only because the denominator shrinks. On the §A agent, keeping the last 10 tool results gives an input bill of 0.63× (total 0.68×).

**Quality.** Not exact. Tokens after the deleted span keep what they absorbed from it; only the keys get a position correction (PatchKV). Leyline reports splices that track the full-context baseline on MLA models.

Tests against full recomputation on agent traces:
- KL divergence and top-1 agreement of next-token distributions;
- task success for the gap variant versus the re-rotation variant;
- a "deleted wrong fact" probe. Where leftover influence would do harm, also append an erratum.

**Prior art.** llama.cpp context shift, StreamingLLM, Leyline, *KV Cache Can Be Editable and Composable*, and KVEraser (which needs a learned editor, so it fails the no-training rule). This adds: billing a splice as a hit, using it to strip reasoning, a gate driven by measured deviation, and the cost comparison against client-side clearing.

## Idea 3: Content-addressed segment cache with a shadow-calibrated gate (own stack or provider, approximate)

**Mechanism.**
1. Cache each document, tool output or memory unit by content hash, prefilled after the shared system prompt (APE style, no training needed).
2. Re-rotate a segment's keys when it appears at a new position.
3. Fix up cross-segment attention with one of:
   - recompute the ~15% most-deviating tokens (CacheBlend);
   - recompute the first tokens of each chunk (EPIC);
   - apply an offset correction (AgentKVShift, 10–30% refreshed; KVCOMM uses the same offset idea for multi-agent prefill).
4. **Gate (new):** on 1% of traffic, also run exact prefill in shadow. Fit a threshold on a cheap deviation signal so that top-1 agreement over the first 64 generated tokens is ≥99%. Requests above the threshold fall back to the exact path, which still gets its prefix hit.
5. Charge two prices: an exact hit and a cheaper approximate hit.

**Cases.** Reordering, insertions, changed segments, and RAG with a new document set per query.

**Hit rate and cost (§E, §I).** In the replay, 98% of document occurrences had been seen before, so segment coverage reaches 96% of document tokens, against 34–60% for exact prefix reuse.

Compute saving per document token, counting the 1% shadow traffic:

| Gate fallback rate f | 0% | 10% | 30% | 50% |
|---|---|---|---|---|
| Saving, s = 0.8 | 2.40× | 2.10× | 1.68× | 1.40× |
| Saving, s = 1.2 | 1.60× | 1.51× | 1.35× | 1.22× |

Assumptions: loading a token costs 0.1, the refreshed fraction is 0.15, and a miss costs 1.0. The method stays ahead at any fallback rate, but the gain shrinks quickly.

Published prefill speedups: CacheBlend 2.2–3.3× time to first token, EPIC up to 8×, CacheSlide 3.1–4.3×, AgentKVShift 2–3.5×.

**Storage:** one KV copy per unique segment. That is 320 KiB per token for Llama-3-70B in BF16, 160 KiB in FP8, and about 69 KB for DeepSeek-V3 (MLA).

**Quality.** The papers report results close to full recomputation on single-hop RAG. Every method leaves a gap on multi-hop and cross-chunk reasoning (Fusion-RAG; AgentKVShift says so itself).

Tests:
- 2WikiMQA, MuSiQue and LongBench against exact prefill;
- KVShareArena;
- the gate's fallback rate in production, which is the real cost driver.

**What this adds.** The gate calibrated by shadow sampling against a stated agreement target, an explicit approximate-hit price, and the saving-versus-fallback curve. Running Idea 1's ordering first means only truly non-prefix tokens take this path.

## Idea 4: Price retention against recompute cost and bandwidth (own stack or provider, exact)

Keep KV in a tier only while expected reuses × recompute cost exceed storage cost × time. Load from a tier only when that is faster than recomputing. §F assumes Llama-3-70B on 8×H100 at $2 per GPU-hour and 45% utilization.

**Recompute cost:**

| Context length | Recompute speed | Cost per 1M tokens |
|---|---|---|
| 8k | 23.7k tokens/s | $0.19 |
| 32k | 19.6k tokens/s | $0.23 |
| 128k | 11.6k tokens/s | $0.38 |

**Retention break-even (BF16; FP8 doubles these windows):**

| Tier | Keep only if reused within |
|---|---|
| GPU memory (HBM) | 1.4 min |
| CPU memory (DRAM) | 6.9 min |
| NVMe SSD | 2.6 h |

**Bandwidth check.** One NVMe drive loads 21k tokens/s in BF16, which is no faster than recomputing. Four drives (85k tokens/s) or 400 Gb/s RDMA (153k tokens/s) do help. This is consistent with the ~1.2× gain from tiered caching that your earlier run measured on real traces.

**Cost versus price.** Recomputing costs the provider about $0.19 per million tokens. That is below a $3/M model's cached-read price of $0.30/M, so the size of the hit discount is a pricing choice, not a cost fact.

**Quality:** unaffected, since the KV is exact. This makes near-100% hits affordable for long-tail sessions, but it creates no hits after middle changes.

## What cannot reach ~100% under these constraints

- **Exact hits after an in-place change.** At every layer from 1 up, the K/V of every later token depend on the changed token. Only layer-0 K/V can be reused exactly, by re-rotation. So an exact method saves at most about 1/L of the suffix work: 1/80 ≈ 1.25% for a 70B model.
- **New document combinations per query.** Exact reuse is capped at 34–60% of document tokens in the replay. Segment reuse reaches ~96%, but only approximately.
- **Multi-hop and cross-chunk reasoning on reused segments.** Every published approximate method leaves a gap, and the savings shrink with the fallback rate.
- **History-rewriting templates on APIs you don't control.**
- **Simultaneous first requests.** On Anthropic, the very first batch of concurrent requests cannot hit. Warming up trades this for latency.
- **Prompts below the minimum cacheable length**, and the last sub-128-token remainder on OpenAI.
- **Cost.** At 100% hits the floor is reads + writes + output (59/28/13%). Going lower needs fewer tokens read (§M, Idea 2) or a lower per-token price (TTL, batch), not more hits. Retention cost (Idea 4) can make 100% uneconomic for sparse reuse.

## What needs a real model

Every quality claim needs a run on a real model, because weights cannot be downloaded here:
- errata semantics and document-order effects;
- keeping reasoning in history;
- the task-success curve of the clearing period;
- splice deviation;
- the segment-reuse gap and the gate threshold.

Token counts use chars/4.

**What was done here:** exact arithmetic, a brute-force check of the ordering rule, a Zipf RAG replay, a bootstrap over small real SWE-agent trajectories, the block-level clearing simulation, and synthetic tests of `cachediff.py`.

**What was not done or not verified:**
- The Mooncake trace was not replayed. Its hashes are chained to the prefix, so it cannot test non-prefix reuse.
- GPU, storage and DRAM prices are assumptions.
- The in-batch hit rate (third-party guides say 30–98%) is not from Anthropic, so measure it from your own usage fields.
- Gemini figures come only from secondary sources.
- A blog's figure of 1.7%→92.2% hits on Codex traces in vLLM is unverified.
