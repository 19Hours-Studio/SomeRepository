# How to make cached context much cheaper, with hits near 100%

I replayed 42 real SWE-agent sessions (Claude Sonnet 4 on SWE-bench Verified, full text, legacy Claude tokenizer). The hit rate on that traffic is already **97.0%**. So the hit rate is not the lever. The big costs are re-reading context you already have and writing new tokens.

## Short answer, by who you are

**1. API user running an agent: 0.88× of the bill without dropping any information.**
- **What to do:** before sending each new tool result or tool input, the client replaces any run of 4 or more lines that already appears verbatim in the context with a pointer: `[n lines identical to lines a–b of message #j]`.
- **Saving:** this cuts the final context by 18%.
- **Against the best prior art:** the closest existing tool is Claude Code's stub for an unchanged re-read of a whole file. Emulated on the same traces it gives 0.993×.
- **If you also clear old content:**

| Setting | My bill | Provider's own context editing at matched keep, best of its swept settings |
|---|---|---|
| References + batched clearing, keep 10 | 0.720× | 1.006× |
| References + batched clearing, keep 3 | 0.625× | 0.868× |

**2. Self-hosted runner or provider: 0.556× of GPU time, with exact output and no information dropped, against a default prefix-cached stack.**
- This combines model-free speculative decoding (suffix or prompt lookup, with the draft length capped) with the references rewrite.
- **Against a stronger baseline:** if your model already ships MTP heads, I model the gain over MTP alone at **0.80×**. The suffix drafter adds 0.91× and references add the rest. Over vLLM's `ngram` drafter at default settings (0.720×), the gain is 0.77×.

**3. RAG that builds a new document combination for each query:** reuse beyond what exact prefix caching gives (34–60%) is only possible approximately. See Idea 3.

**Two hard limits:**
- No exact method can reuse KV computed after a token that changed in place. If you need "near 100% hits and exact" after a middle change, the client must append a correction (an erratum) instead of editing in place.
- On agent traffic, **56% of the bill is cache reads and 58% of runner GPU time is work on cached context**. The levers are therefore:
  - send fewer tokens (references, clearing);
  - re-read the cache fewer times per output token (speculation);
  - make each read cheaper (4-bit KV).

## Idea A: "Reference, don't repeat" for tool traffic (client only; information-exact; KV exact) — new

**Mechanism.**
- When a tool result or tool input arrives, find each maximal run of ≥ MINRUN lines that occurs verbatim and contiguously in an earlier message of the same request.
- Line numbers from `cat -n` are part of the match, so a shifted line never matches.
- Replace the run with a short pointer.
- Do this once, on arrival, and keep the rewritten text. History stays append-only, so the prefix cache is never broken.

**Where the repeats come from.** Re-viewing files, the edited snippet the editor echoes back after an edit, overlapping view ranges, re-run test output, and `old_str`/`file_text` payloads that copy earlier content. Measured shares:
- 17.5% of tool-result tokens;
- 25% of tool-input tokens;
- 18.1% of the final context overall.

**Measured on the 42 sessions** (`calc.py` §R):

| Variant | Bill vs as-sent | Runner GPU time |
|---|---|---|
| Whole-result duplicate stub (Claude Code Read dedup, emulated) | 0.993× | — |
| References, MINRUN = 8 | 0.897× | — |
| **References, MINRUN = 4** | **0.881×** (hit 97.1%) | 0.887× |
| References, MINRUN = 2 | 0.873× | — |
| + batched clearing of results and inputs, keep 10 | **0.720×** (0.801× without references) | — |
| + batched clearing, keep 3 | 0.625× (0.647× without references) | — |
| + suffix speculation, capped | — | **0.556×** |
| + suffix speculation + 4-bit KV | — | 0.489× (approximate KV) |

**What it covers.**
- It covers tool outputs that repeat earlier content.
- It covers neither middle edits nor reordering; for those, see Idea 1.
- It does not raise the hit rate. It shrinks what is written once and then re-read on every later step.

**Where it runs and what it costs.**
- It sits in the agent harness and works on any API.
- A runner that owns the agent can use it too.
- CPU: a line index over the session text, a few MB. The full 42-session run took 16 seconds in pure Python, including tokenization.
- No GPU or storage cost. Fewer tokens also mean a lower time to first token.

**Quality.**
- No information leaves the context. But the model has to follow a pointer instead of reading the text next to where it is working.
- The main risks are exact copying for `str_replace` (the model must reproduce `old_str` from an earlier copy) and reasoning about long-range positions.
- Under clearing, a pointer can dangle for up to K turns once its target is cleared. Keep-all, which gives 0.881×, has no such problem.
- **Test:** run an A/B on SWE-bench Verified (resolve rate) and also measure:
  - the rate of `No replacement was performed` errors;
  - the number of steps per task;
  - a pointer-following probe: ask for a line that exists only behind a pointer.

**Prior art and what this adds.**
- Claude Code (v2.1.86 and later) deduplicates unchanged re-reads of a whole file, keyed on file modification time. Users have reported stale results after external edits and after rewinds.
- Diff-based editing formats exist (for example Aider), and so does LZ77-style compression.
- This approach adds:
  - line-run granularity, which saves 12× more than whole-result stubs on these traces;
  - matching on content rather than modification time, so it cannot go stale;
  - persistence that is safe for the cache;
  - composition with clearing and speculation;
  - a measured replay.

## Idea B: Batched clearing of old tool results and inputs (client only; KV exact; content dropped on purpose)

**Mechanism.**
- Every T steps, replace all tool results and inputs older than the last K with placeholders of about 20 tokens. Keep those placeholders.
- Put an explicit cache breakpoint at the first block that has not been cleared. Without it, the next clear point is about 24 blocks back, beyond Anthropic's 20-block lookback.
- The best T follows the economic-order-quantity rule T* ≈ √(2·1.25·K/(0.1·g)). Here K is the kept window that is rewritten at each clear and g is the clearable tokens added per step. The rule predicts 9 and the replay finds 9.

**Results against the provider's tool at its best settings** (`calc.py` §S; Anthropic `clear_tool_uses`, which is stateless: the client keeps the full history and the server clears on every request over the trigger):

| Keep | Content | Provider best (setting) | Client batched | Ratio |
|---|---|---|---|---|
| 1 | results + inputs | 0.533× (trigger 5k) | 0.533× | 1.00 |
| 3 | results + inputs | 0.868× (trigger 5k, `clear_at_least` 20k) | 0.647× (T = 9) | **0.745** |
| 10 | results + inputs | 1.006× (trigger 100k) | 0.801× (T = 17) | **0.796** |
| 10 | results | 1.007× | 0.880× (T = 18) | 0.874 |

**Why `clear_at_least` doesn't rescue the provider tool.** Under stateless semantics, once the history is large, clearing everything older than `keep` always frees more than the threshold. The cleared boundary therefore still moves forward one turn per step, and every step rewrites about K results. I inferred these semantics from the docs. Check them with `cache_read_input_tokens`.

**Other measurements.**
- Floor for any policy that reduces context: 0.466×. Output alone is 0.220× of the bill.
- Sessions of 80 steps or more: 0.568× (results + inputs, keep 3).

**Quality.**
- *The Complexity Trap* masks observations with a window of M = 10 and matches or slightly beats the raw agent (Qwen3-Coder 480B: 53.8% → 54.8%). It masks no tool inputs.
- Batched keep-10 always shows a superset of rolling keep-10, so the 0.880× result-only setting is plausibly covered by that evidence.
- Keep 3, and clearing inputs at all, are untested.
- **Lower-risk variant:** clear only inputs over 200 tokens. That gives 0.671× at keep 3.
- **Test:** resolve rate over {results, results + inputs, inputs over 200 tokens} × keep {3, 10} × batched vs rolling, with cost taken from the usage fields.

## Idea C: Runner — speculative decoding with drafts copied from the context (own stack or provider; lossless)

**Mechanism.** Draft up to 8 tokens by suffix-matching the last 1–4 tokens against the prompt, the output so far, and earlier sessions' outputs (SuffixDecoding-style corpus). Verify in one pass.

**Why the replay is exact without a model.**
- With a deterministic draft d, standard speculative sampling accepts d with probability p(d).
- "Sample y ~ p and accept if y = d" is the same algorithm.
- So replaying the realized outputs gives the exact distribution of accepted lengths for this tokenizer. These runs were at temperature 0.

**Tokens per verify pass** (measured on 558,115 output tokens):

| Drafter | Tokens per pass |
|---|---|
| Prompt lookup | 2.26 |
| + cross-session corpus | 2.46 |
| With old results and inputs cleared | 1.96 |

So if a runner clears context itself, it should keep the full text for drafting.

**Roofline GPU time vs prefix cache + FP8 KV without speculation** (70B dense model on 8×H100; prefill at 45% MFU; decode at 70% of HBM bandwidth; 32 concurrent sequences; decoded-token KV reused):

| Configuration | GPU time |
|---|---|
| vLLM `ngram`-style prompt lookup | 0.720× |
| + cross-session corpus | 0.708× |
| **+ draft capped at ⌊t_mem/t_token⌋ − 1** | **0.626×** |
| + references (Idea A) | **0.556×** |
| + 4-bit KV (approximate) | 0.489× |
| Speculation + splicing results and inputs + 4-bit (approximate, content dropped) | 0.406× |

**How the gain depends on concurrency** (capped drafts): 0.519× at 8 sequences, 0.626× at 32, 0.676× at 128.

**Against an MTP-equipped runner** (modelled: one MTP token accepted with p = 0.75–0.90, per the DeepSeek-V3 report):

| Configuration | vs no speculation | vs MTP alone |
|---|---|---|
| MTP alone | 0.68–0.71× | 1 |
| Hybrid: suffix where a match exists, else MTP | 0.622× | 0.88–0.92× |
| Hybrid + references | 0.552× | **0.78–0.82×** |

**Details.**
- **Where it runs and what it costs:** a vLLM config change (`speculative_config` with `ngram`, or `suffix` via Arctic Inference). It needs no extra GPU memory beyond verify buffers. The CPU drafter takes about 20 µs per token (Snowflake's figure), and the suffix tree lives in CPU memory. Latency per token goes down.
- **Cases covered:** all of them, because it acts on decode and does not depend on hits.
- **Quality:** the output distribution is identical; only numerics differ, as with any change in batch shape.
- **Test:** run with and without speculation on replayed traces. Compare outputs at temperature 0, read `spec_decode_num_accepted_tokens`, and measure GPU-seconds per session.
- **Prior art:** prompt-lookup decoding (PLD) and SuffixDecoding. SuffixDecoding's authors report 2.45× on SWE-bench against 1.50× for PLD. An independent study measured 2.14× for suffix decoding against 1.44× for PLD and 0.90× for EAGLE-3.
- **What this adds:** the cap on draft length, the dependence on concurrency, the replay method that needs no model, the effect of clearing on drafting, and composition with references.

**Limits of these numbers.**
- The roofline model is a model, not a measurement.
- The outputs are Claude's, and your model's copying rate will differ.
- MTP acceptance is assumed, not replayed.
- Speculation gives API users nothing on cost.

## §0. Levers that don't depend on layout (API; `calc.py` §G–L)

- **Measure hits:**
  - Anthropic: `cache_read_input_tokens / (cache_read + cache_creation + input_tokens)`.
  - OpenAI: `cached_tokens / prompt_tokens`. From GPT-5.6 on, OpenAI also reports `cache_write_tokens` and bills writes at 1.25×.
- **1-hour TTL** when gaps between reuses exceed 5 minutes. At 5 reuses, the 5-minute TTL costs 7.5× against 2.5× for the 1-hour TTL.
- **Warm up before fan-out:** send one `max_tokens=1` request first. This makes the shared prefix 1.9× cheaper at N = 2 and 10.2× at N = 50.
- **Batch API plus caching:** breaks even at about 81% in-batch hits. Warm up synchronously with the 1-hour TTL first.
- **OpenAI routing:** keep to about 15 requests per minute or fewer per `prompt_cache_key`, and shard with a stable mapping.
- **Minimum length:** prompts below 1,024 tokens (4,096 for some Anthropic models) are never cached.

## Idea 1: Cache-stable layout (client only, exact)

- **Errata instead of in-place edits** for middle edits, insertions and changed tool output. A 500-token erratum in a 74k prompt keeps about 99.3% hits on that turn.
- **Fold errata back in** after T* = (1.15·S − 1.25·e)/(0.1·e) turns, where e is the erratum size and S the tokens after the edit. This is a ski-rental rule, at most 2× the best schedule in hindsight.
- **Canonical order** for documents already seen, so reordering costs nothing.
- **Normalize** timestamps, IDs and JSON key order.
- **Order blocks** by p/((1−p)·s), ascending, where p is the chance a block changes and s its size. This was optimal in 3,000 of 3,000 brute-force layouts.
- **Volatile tail** below the last breakpoint, billed at 1.0× rather than written at 1.25×.
- **Use up to 4 breakpoints**, because of the 20-block lookback.
- **Keep reasoning in the template.** Templates that strip it cost 1.27× per input token at 5 tool steps per query.
- **`cachediff.py`** finds the first breaking block and its likely cause.

On agent traffic this mostly prevents breaks; there is little average hit rate left to win. The quality risk is in the prompt text itself, not in the KV: a stale fact next to its correction. Test that with a needle test that places a superseded fact next to its erratum.

Prior art: Manus, Anthropic docs, *Don't Break the Cache*, RAGCache, RAGBoost, CacheWeaver.

## Idea 2: Delete and splice KV in place (runner, approximate)

- **Mechanism:** drop the span's KV pages, re-rotate the RoPE keys after the span (or leave a position gap), and prefill only the replacement.
- **Effect:** the bill-equivalent drops to 0.561× against 0.647× for batched clearing. GPU time reaches 0.406× with speculation and 4-bit KV.
- **Quality:** not exact, because later tokens keep what they absorbed from the deleted span. Leyline, KV-Editable and PatchKV report results close to full recomputation; I took that from their abstracts and did not reproduce it.
- **Gate:** recompute 1% of requests exactly and ship only if top-1 agreement is ≥ 99%.

## Idea 3: Content-addressed segment cache with a shadow-calibrated gate (runner, approximate)

**Mechanism.**
- Cache each document or tool output by content hash, prefilled after the shared system prompt (APE-style, no training).
- Re-rotate a segment's keys when it appears at a new position.
- Fix cross-segment attention with CacheBlend (about 15% of tokens recomputed), EPIC or AgentKVShift.
- **Gate:** run exact prefill in shadow on 1% of traffic and fit a threshold on a cheap deviation signal so that top-1 agreement is ≥ 99%. Requests above the threshold fall back to exact prefill.
- Charge two prices: an exact hit and a cheaper approximate hit.

**Coverage (synthetic Zipf replay):** about 96% of document tokens, against 34–60% for exact prefix reuse.

**Saving vs fallback rate:**

| Popularity skew | Fallback 0% | Fallback 50% |
|---|---|---|
| s = 0.8 | 2.40× | 1.40× |
| s = 1.2 | 1.60× | 1.22× |

**Quality:** weakest on multi-hop reasoning. Test on 2WikiMQA, MuSiQue, LongBench and KVShareArena. For agents, Idea A gets most of the repeated-content saving exactly and on the client, so Idea 3 pays off mainly for RAG.

## Idea 4: Price retention against recompute cost (runner, exact)

Keep KV in a tier only while expected reuses × recompute cost exceed storage cost × time. These use assumed prices.

| Tier | Keep only if reused within (BF16) |
|---|---|
| GPU memory (HBM) | 1.4 min |
| CPU memory (DRAM) | 6.9 min |
| NVMe SSD | 2.6 h |

One NVMe drive loads about 21k tokens/s, which is no faster than recomputing. This agrees with the ~1.2× gain from tiering in your earlier run. Tiering makes long-tail hits affordable but creates no new hits after middle changes.

## What cannot reach ~100%, or a large gain, under these constraints

- **Exact hits after an in-place change:** capped at 1/L of the suffix work (1/80 for a 70B model).
- **Hit rate as the lever on agent traffic:** it is already 97%.
- **API bills below 0.466×** without dropping the current turn or cutting output, which is 22% of the bill.
- **Information-exact savings on the API:** 0.88× (Idea A). Anything lower drops content.
- **Keep 1:** the provider's own tool already reaches 0.533×, so client-side work adds nothing there.
- **Against MTP runners:** the measured-plus-modelled gain is about 0.80×, not 0.56×. It shrinks at high concurrency.
- **New document combinations per query:** reuse beyond 34–60% is only approximate.
- **Other hard limits:** concurrent first requests, prompts below the minimum length, and templates that rewrite history on APIs you don't control.

## What needs a real model

- Resolve rate and the `str_replace` failure rate with references.
- Resolve rate for clearing at keep 3 vs keep 10, results vs inputs.
- Speculative acceptance and GPU-seconds in vLLM for your own model, including real MTP acceptance.
- Splice deviation (KL divergence, top-1 agreement).
- 4-bit KV quality.
- The effects of errata and document order.
- The gate threshold for segment reuse.

**What was done here:**
- Real-trace replays with a real tokenizer.
- A check of the bill model against SWE-agent's logged cost: $38.01 modelled against $50.63 logged, a ratio of 0.75 that ranges only 0.70–0.77 across sessions. Ratios therefore hold, while absolute token counts are about 25% low.
- Exact, model-free replays of speculative acceptance and of references.
- The roofline model.
- Brute-force checks of the ordering rule.
- The Zipf RAG replay.

**What was not verified:**
- Claude's current tokenizer (I used the legacy one).
- The size of the tool schema.
- The stateless semantics of context editing.
- In-batch hit rates.
- GPU and storage prices.
