# How to make cached context much cheaper, with hits near 100%

This version replays the same 42 real SWE-agent sessions (Claude Sonnet 4, SWE-bench Verified), this time on the full text with a real tokenizer. It finds two levers the previous version left unused:

- **Runner side, lossless:** speculative decoding with drafts copied from the context itself. Each decode pass reads the cached KV once and emits about 2.5 tokens. On these traces that gives **0.66× GPU time with no change to the output**. The previous best exact figure was 0.84×, and it worked by dropping content.
- **API side:** clear old **tool inputs** as well as old tool results, in batches. Tool inputs are 21% of the context. This gives **0.65× of the bill**, against 0.76× for results only. Compared with Anthropic's own context editing at its best setting I tested (0.874×), it is **0.74×**.

**Files** (in `round6/`):
- `calc.py` runs in about 3 minutes (`python3 -I calc.py`), and its output is in `calc_out.txt`. Sections P and Q are new.
- `traces/c4/extract2.py` rebuilds `traces/c4/steps2.json` from the 42 public `.traj` files in `s3://swe-bench-submissions` (keys in `pick.txt`). It uses the legacy Claude tokenizer that ships in the `anthropic==0.30.0` wheel on PyPI.
- `cachediff.py` and `examples/` are unchanged.

## Short answer, by who you are

| You are | Best gain over current best practice (measured on the 42 traces) | Exact? |
|---|---|---|
| **Runner (self-hosted or provider)** | **0.66× GPU time.** Use model-free speculative decoding (vLLM `ngram`, or `suffix` with Arctic Inference) with the draft length capped. Add batched clearing for 0.54×, or splicing plus 4-bit KV for 0.44× | Speculation is lossless. Clearing drops content; splicing and 4-bit are approximate |
| **API user (agent)** | **0.647× bill**: clear old tool results *and* inputs every 9 steps, keep 3. Sessions of 80 steps or more: 0.568×. A safer variant keeps the Complexity-Trap window of 10: 0.801× | KV is exact; content is dropped on purpose |
| **RAG with a new document combination per query** | Segment cache with a gate (Idea 3), approximate | Approximate |

**Key fact 1.** No exact method can reuse KV after a token that changed in place. At most 1/L of the suffix work can be saved (1/80 for a 70B model). "Near 100% hits and exact" after a middle change requires the client to append errata instead of editing.

**Key fact 2.** On real agent traffic the hit rate is already **97.0%**. The bill splits into reads 56%, writes of new tokens 22% and output 22%. On the runner, **56% of GPU time is work on cached context**, and most of that is decode re-reading the KV cache. The large levers are therefore: read each cached token fewer times per generated token (speculation), read fewer cached tokens (clearing), or make each read cheaper (4-bit KV). A higher hit rate is not one of them.

## §R. Runner: lossless speculative decoding on agent traffic (`calc.py` §Q)

**Mechanism.**
- Draft up to k tokens by matching the last 1–4 generated tokens against the request's own token stream (prompt plus output so far). This is prompt-lookup decoding.
- Optionally also match against earlier sessions' outputs. This is the idea behind SuffixDecoding's cross-request corpus.
- Verify the whole draft in one forward pass, which reads the cached KV and the weights once for all k+1 positions.

**Why the replay is exact without a model.**
- With a deterministic draft d, speculative sampling accepts d with probability p(d). "Sample y ~ p, accept iff y = d" is the same algorithm.
- So replaying the realized outputs gives the exact accepted-length distribution for that model and tokenizer.
- These runs used temperature 0.

**Measured on 558,115 output tokens:**

| Drafter | Tokens per verify pass |
|---|---|
| Prompt lookup | 2.26 |
| + earlier sessions' outputs | 2.46 |
| Prompt only shows the last 3 results | 2.47 (old observations contribute little) |
| Prompt only shows the last 3 results and last 3 inputs | **1.96** (the model copies its own earlier edit inputs) |

**Roofline GPU time, relative to prefix caching with FP8 KV and no speculation.** Assumptions as in round 5: 70B dense model on 8×H100, prefill at 45% MFU, decode at 70% of HBM bandwidth, 32 concurrent sequences.

| Runner configuration | GPU time | Decode |
|---|---|---|
| Speculation, draft ≤8 | 0.737× | 0.57× |
| **+ draft capped at ⌊t_mem / t_token⌋ − 1, so verify stays memory-bound** | **0.663×** | 0.45× |
| 4-bit KV alone (approximate) | 0.786× | 0.65× |
| Speculation + 4-bit KV | 0.592× | 0.34× |
| Batched clear, results, keep 3 (content dropped) | 0.818× | 0.64× |
| Speculation + batched clear, results | 0.615× | 0.31× |
| **Speculation + batched clear, results and inputs** (drafting at 1.96) | **0.544×** | 0.31× |
| Speculation + splice results and inputs + 4-bit KV | **0.436×** | 0.23× |

**How the gain depends on concurrency:**

| Concurrent sequences | Speculation | Capped |
|---|---|---|
| 8 | 0.549× | 0.549× |
| 32 | 0.737× | 0.663× |
| 128 | 0.853× | 0.713× |

Verify FLOPs start to bind at large batches, so cap the draft length there.

- **Where it runs:** own serving stack or provider. It is a config change in vLLM (`speculative_config` with `method: "ngram"` or `"suffix"`).
- **Costs:** no GPU memory beyond small verify buffers. The CPU drafter is about 20 µs per speculated token (Snowflake's figure for suffix decoding), and the suffix-tree corpus lives in CPU memory. Latency per token goes down.
- **Cases covered:** every case, including middle edits, because it acts on decode. It does not depend on hits at all.
- **Quality:** identical output distribution. Lossless speculative sampling is a theorem; only numerics differ, as with any change of batch shape.
- **Test:** run vLLM with and without speculation on replayed traces. Compare outputs at temperature 0, read the acceptance metrics, and measure GPU-seconds per session.
- **Approximations in my numbers:**
  - The cap assumes that a truncated run of accepted tokens is re-drafted on the next pass.
  - The tokenizer is a proxy.
  - The outputs are Claude's. Your model's copying rate will differ, so measure it.
- **Prior art and what this adds:**
  - Prior art: prompt-lookup decoding, SuffixDecoding (authors' own numbers: 1.8–4.5× speculative speedup on an OpenHands SWE-bench run in vLLM), and adaptive draft lengths.
  - Added here:
    - It is framed as the **largest exact lever on the cost of cached context**, larger than tiering (~1.2×) or 4-bit KV, with no quality loss.
    - A model-free, exact replay method on public traces.
    - The finding that **clearing tool inputs cuts drafting from 2.46 to 1.96**. A runner that clears context itself should keep the full text for drafting.
    - The concurrency dependence.
- **Honest limit:** if you already run EAGLE or MTP speculation, the extra gain is unmeasured here. SuffixDecoding reports beating EAGLE-2/3 on agentic workloads and composing with it.

## §N. API: what to clear, and how (`calc.py` §P)

**Composition of the final context:**

| Part | Share |
|---|---|
| Tool results | 73.5% |
| Tool inputs (edit payloads, file contents in `create`) | 21.0% |
| Thoughts | 4.0% |
| Task | 1.4% |

Mean final context is 50k tokens. 2,441 of 2,458 step transitions are strictly append-only.

**Bills relative to "as sent"** (append-only, `cache_control` on the last 2 messages, 97.0% hits). Multipliers: write 1.25×, read 0.1×, output 5×.

| Policy | Rolling (every step) | **Batched**, best T | Server splice (runner only) |
|---|---|---|---|
| Clear results, keep 3 | 1.009 | 0.763 (T=9) | 0.654 |
| Clear results, keep 10 (Complexity-Trap window) | **1.981** | 0.880 (T=18) | 0.722 |
| **Clear results and inputs, keep 3** | 0.916 | **0.647** (T=9) | 0.561 |
| Clear results and inputs, keep 10 | 1.909 | 0.801 (T=17) | 0.650 |
| Clear results and inputs over 200 tokens, keep 3 | 0.813 | 0.671 (T=9) | 0.577 |
| Clear results and inputs, keep 1 | 0.533 | 0.533 | 0.532 |

**Fair competitor: Anthropic context editing at its best settings.** It is stateless: each request is cleared again from the full history, so the cleared set rolls forward one turn per step.

| Trigger | Results only | Results and inputs |
|---|---|---|
| 20k | 0.972 | **0.874** |
| 30k | 0.989 | 0.899 |
| 50k | 0.996 | 0.952 |
| 100k | 0.998 | 0.996 |

Batched client-side clearing with the same keep-3 content reaches 0.647/0.874 = **0.74× of the provider's best**. The 20k trigger keeps more context below the trigger, so this comparison is close but not identical in content.

**Ceiling.**
- No context-reduction policy can go below **0.466×**: system prompt, task and newest turn only, all hits. Output alone is 0.220×.
- Batched clearing of results and inputs gets 66% of the way to that floor.
- In the 7 sessions with 80 steps or more: results only 0.719×, results and inputs 0.568×, results and inputs keeping 10 0.701×.

**Period rule.** T* ≈ √(2·1.25·K/(0.1·g)), where K is the kept window rewritten at each clear and g the clearable tokens added per step. It predicts 9; the replay's best is 9. This is the EOQ formula, applied rather than invented.

**How to run it on Anthropic.**
- Clear on the client and persist the placeholders, so history stays append-only between clears.
- Use placeholders of about 20 tokens, such as `[str_replace on path X, 37 lines; content cleared]`.
- Put one explicit breakpoint at the first uncleared block. Without it, the next clear point is about 24 blocks back, beyond the 20-block lookback.
- Verify with `cache_read_input_tokens`.

**Quality.**
- *The Complexity Trap* masks observations with M=10 and matches or slightly beats the raw agent (for example Qwen3-Coder 480B: 53.8% → 54.8%). It does not mask tool inputs and does not discuss caching.
- Batched keep-M always shows a superset of rolling keep-M (between M and M+T observations), so the published result plausibly carries over to the 0.880× and 0.801× settings. The second one also clears inputs, which is untested.
- Keep 3 and clearing inputs are below or outside any published setting.
- The over-200-token variant (0.671×) keeps the short command trail and drops only bulky payloads. It is the lower-risk way to clear inputs.
- **Test:** SWE-bench Verified resolve rate for {results, results and inputs, inputs over 200 tokens} × keep {3, 10} × batched versus rolling, with cost from the usage fields.

## §O. Where the runner's GPU time goes

- Baseline: prefill 39%, decode 61%, cached-context work 56%.
- No prefix cache would cost about 11.4× (round-5 figure).
- After prefix caching, the dominant cost of reused context is decode re-reading the cached KV, which grows with context × output tokens. Speculation (§R) divides the number of passes by the tokens emitted per pass. Clearing shrinks the context, and 4-bit KV shrinks the bytes.
- Your earlier run found that KV compression without retraining bottoms out at about 2.6–3 bits, so 4-bit is near the useful limit.
- Shared-prefix cascade attention (FlashInfer, vLLM heuristic) helps only with fan-out on a long common prefix. These traces have almost none, so I claim no gain from it.

## §0. Levers that don't depend on layout (API; arithmetic in `calc.py` §G–L)

- **Measure hits** from the usage fields:
  - Anthropic: `cache_read_input_tokens / (cache_read + cache_creation + input_tokens)`.
  - OpenAI: `cached_tokens / prompt_tokens`. From GPT-5.6 on, OpenAI also reports `cache_write_tokens` and bills writes at 1.25×.
- **1-hour TTL** when reuse gaps exceed 5 minutes. At N=5 reuses: 7.5× with the 5-minute TTL against 2.5× with the 1-hour TTL.
- **Warm-up before fan-out:** one `max_tokens=1` request first. Concurrent first requests all write. This makes the shared prefix 1.9× cheaper at N=2 and 10.2× at N=50.
- **Batch API plus caching:** break-even is about 81% in-batch hits. Warm up synchronously with the 1-hour TTL first, and measure your own in-batch rate.
- **OpenAI routing:** about ≤15 requests per minute per `prompt_cache_key`. Shard with a stable mapping.
- **Minimum length:** prompts below 1,024 tokens (4,096 for some Anthropic models) are never cached.

## Idea 1: Cache-stable layout (client only, exact)

- **Errata instead of in-place edits** for middle edits, insertions and changed tool output. A 500-token erratum in a 74k prompt keeps about 99.3% hits on that turn.
- **Canonical order** for documents already seen, so reordering costs nothing.
- **Normalize** timestamps, IDs and JSON key order.
- **Order blocks** by p/((1−p)·s), ascending, where p is the chance a block changes and s its size. This is the textbook exchange rule, and it was optimal in 3,000 of 3,000 brute-force layouts.
- **Volatile tail** below the last breakpoint, billed at 1.0× rather than written at 1.25×.
- **Fold errata back in** after T* = (1.15·S − 1.25·e)/(0.1·e) turns, where e is the erratum size and S the tokens after the edit (ski rental, at most 2× the best schedule in hindsight).
- **Use up to 4 breakpoints**, because of the 20-block lookback.
- **Keep reasoning in the template.** Templates that strip it cost 1.27× per input token at 5 tool steps per query.
- **`cachediff.py`** finds the first breaking block and its likely cause.

On real agent traffic this mainly **avoids breaks**; there is little average hit rate left to win. Quality risks are in the prompt text itself (stale text beside its correction, popularity order), not in the KV. Test with a needle test placing a superseded fact next to its erratum.

Prior art: Manus, Anthropic docs, *Don't Break the Cache*, RAGCache, RAGBoost, CacheWeaver.

## Idea 2: Delete and splice KV in place (runner, approximate)

**Mechanism:** drop the span's KV pages, re-rotate RoPE keys after the span or leave a position gap, then prefill only the replacement.

**Effect:** no rewrite cost.
- Bill: 0.561× (results and inputs), against 0.647× batched.
- GPU time: 0.436× when combined with speculation and 4-bit KV.

**Quality:** not exact, because later tokens keep what they absorbed from the deleted span. Leyline, KV-Editable and PatchKV report results close to the full-context baseline (from abstracts, not reproduced here).

**Gate:** sample 1% of requests for exact recomputation and compare. Ship only if top-1 agreement is ≥99%.

## Idea 3: Content-addressed segment cache with a shadow-calibrated gate (runner, approximate)

**Mechanism.**
- Cache each document or tool output by content hash, prefilled after the shared system prompt (APE style, no training).
- Re-rotate a segment's keys when it appears at a new position.
- Fix up cross-segment attention with CacheBlend (~15% of tokens recomputed), EPIC (first tokens of each chunk) or AgentKVShift (offset correction).
- **Gate:** exact prefill in shadow on 1% of traffic. Fit a threshold on a cheap deviation signal so that top-1 agreement is ≥99%; requests above it fall back to exact prefill.
- Charge two prices: an exact hit and a cheaper approximate hit.

**Coverage (Zipf replay, synthetic):** about 96% of document tokens, against 34–60% for exact prefix reuse.

**Saving versus gate fallback rate:**

| Popularity skew | Fallback 0% | Fallback 50% |
|---|---|---|
| s = 0.8 | 2.40× | 1.40× |
| s = 1.2 | 1.60× | 1.22× |

**Quality:** weakest on multi-hop and cross-chunk reasoning. Test on 2WikiMQA, MuSiQue, LongBench and KVShareArena. This pays off only for RAG and shared memory: in the agent traces, 17 of 2,458 transitions break, all at the tail.

## Idea 4: Price retention against recompute cost (runner, exact)

Keep KV in a tier only while expected reuses × recompute cost exceed storage cost × time (assumed prices).

| Tier | Keep only if reused within (BF16) |
|---|---|
| GPU memory (HBM) | 1.4 min |
| CPU memory (DRAM) | 6.9 min |
| NVMe SSD | 2.6 h |

One NVMe drive loads about 21k tokens/s, which is no faster than recomputing. This agrees with the ~1.2× gain from tiering in your earlier run. It makes long-tail hits affordable but creates no new hits after middle changes.

## What cannot reach ~100%, or a large gain, under these constraints

- **Exact hits after an in-place change:** capped at 1/L of the suffix work.
- **Hit rate as the lever on agent traffic:** it is already 97%.
- **API bills below 0.466×** without dropping the current turn or cutting output, which is 22% of the bill.
- **Exact API savings** come only from dropping content: 0.647–0.880× depending on how much is kept.
- **Speculation's gain shrinks at high concurrency** (0.71× at 128 sequences, capped). It depends on your model's copying behaviour, and it gives API users nothing on cost.
- **New document combinations per query:** reuse beyond 34–60% is approximate.
- **Other hard limits:** concurrent first requests, prompts below the minimum, and history-rewriting templates on APIs you don't control.

## What needs a real model

- Speculation acceptance and GPU-seconds for your own model in vLLM (metrics `spec_decode_num_accepted_tokens`).
- Resolve rate for clearing results versus results and inputs, keep 3 versus 10, batched versus rolling.
- Splice deviation (KL divergence, top-1 agreement).
- 4-bit KV quality.
- Errata and document-order effects.
- The gate threshold for segment reuse.

**What was done here:**
- Real-trace replays with a real tokenizer.
- A check of the bill model against logged cost.
- An exact, model-free replay of speculative acceptance.
- The roofline model.
- A brute-force check of the ordering rule.

**What was not verified:**
