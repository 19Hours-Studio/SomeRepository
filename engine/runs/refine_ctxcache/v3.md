# How to make cached context much cheaper, with hits near 100%

I rebuilt every number in this directory. Running `python3 -I calc.py` takes about 2 minutes and needs only the standard library. The output is in `calc_out.txt`, and the SWE-agent trajectories are in `traces/`. The new `cachediff.py` finds where one request breaks the cache relative to the previous one; `examples/` holds three test pairs. Nothing was committed.

Changes from the previous version:
- Cache writes now include the previous turn's output, so the bill split changed slightly.
- Three new mechanisms that break the cache are measured: Anthropic's breakpoint lookback, chat templates that strip earlier reasoning, and the cache-write premium on the volatile tail.
- Idea 3 now has a cost-versus-fallback-rate curve.
- The OpenAI claims are checked against OpenAI's documentation.
- KVCOMM is added as prior art.

---

## Short answer, by who you are

| You are | What gets you to ~100% hits | Exact? |
|---|---|---|
| **API user** | Idea 1: never edit what was already sent, put volatile blocks last, add errata instead of edits, place breakpoints carefully, choose TTL and cache keys. Find each break with `cachediff.py`. | Yes |
| **Self-hosting** | Idea 1, plus a chat template that doesn't rewrite history (send token IDs if needed), plus Idea 2 (splice KV in place) and Idea 4 (retention by cost) | Ideas 1 and 4 exact, Idea 2 approximate |
| **Provider** | All of the above, plus Idea 3 (a segment cache with a gate calibrated in production), sold as a cheaper "approximate hit" tier | Idea 3 approximate, gated |

**Key fact:** no exact method can reuse KV after a token that changed in place. The limit is in Ideas 1 and 4 and in the closing section on what can't reach 100%. So "near-100% and exact" is only possible if the client stops changing content in place. Every server-side method for real middle changes is approximate. It must be checked against full recomputation and priced separately.

**Second key fact:** at 100% hits the input bill is mostly cached reads and writes. So "much cheaper" also means *reading fewer tokens*, which a higher hit rate can't do.

## 0. What the bill is made of at 100% hits (`calc.py` §A)

The model is a 50-turn agent:
- a 10k-token system prompt, plus 2k tokens of tool output and 300 output tokens per turn;
- Anthropic-style multipliers: write 1.25×, read 0.1×, output 5× the base input price;
- each turn's output is written to the cache on the next turn.

**The bill splits into reads 59%, writes 28%, output 13%.** None of these shrink with a higher hit rate. Deleting all but the last 10 turns' tool results and outputs in place (Idea 2) cuts the input bill to **0.63×** (total 0.68×) at the same hit rate.

**Measure the hit rate from usage fields:**
- Anthropic: `cache_read_input_tokens / (cache_read + cache_creation + input_tokens)`.
- OpenAI: `cached_tokens / prompt_tokens`. From GPT-5.6 on, OpenAI also reports `cache_write_tokens` and charges writes at 1.25× (confirmed in OpenAI's documentation).

**Levers that don't depend on layout:**
- **TTL (§G).** Take a context reused N times at 6–60-minute gaps. With a 5-minute TTL it costs 1.25·(N+1) per token, which is 7.5× at N=5. With a 1-hour TTL it costs 2 + 0.1·N, which is 2.5× at N=5.
- **Routing.** OpenAI asks you to keep each `prompt_cache_key` to about 15 requests per minute. Above that, requests miss even with an identical prefix. Split the traffic over ⌈rate/15⌉ keys with a stable mapping. On GPT-5.6 and later, a stable key is also required for the more reliable matching.

## Idea 1: Cache-stable prompt layout (client only, exact)

**Where it runs and what it costs:** any API. No extra memory or storage, and latency is the same or lower.

**1a. Ordering rule.** Assume each block i (size sᵢ) changes independently with probability pᵢ per request.
- An exchange argument on neighbouring blocks shows the best order sorts blocks by **pᵢ / ((1−pᵢ)·sᵢ) ascending**: the odds of a change per token, not the probability.
- Brute force over 3,000 random 6-block layouts (§C): this rule was optimal in all of them.
- The plain p/s rule was suboptimal in 59% of layouts, by a median of 1% and at most 17%.

**1b. Volatile tail and diff-only re-sending.**
- Put the to-do list, memory and current state after the conversation.
- Re-send a block only when it changed, as a diff.
- **Put the last cache breakpoint before the tail.** On Anthropic, tokens after the last breakpoint are billed as plain input (1.0×) instead of a write (1.25×). Re-sent tail tokens are never read back, so this saves 20% of the tail's cost (§J).

**1c. Append-only errata and normalization.**
- Turn a middle edit, an insertion or a changed tool output into a short note at the end, such as `[supersedes tool_result #17]: …`.
- Normalize timestamps, UUIDs, JSON key order and unordered listings.
- Serialize document sets in a canonical order.

**1d. Compaction by ski rental.**
- Fold the errata back into place after T* = (1.15·S − 1.25·e)/(0.1·e) turns, where e is the erratum size and S is the number of tokens after the edit point.
- Examples: S = 50k with e = 500 gives 1,138 turns. S = 10k with e = 2k gives 45 turns. If S ≤ e, rewrite now.
- Rewriting at T* costs at most 2× the best schedule in hindsight.

**1e. Failure modes that break the cache without any edit you meant to make.**
- **Anthropic breakpoint lookback.** Hits are looked for only about 20 content blocks back from each breakpoint (per Anthropic's documentation). In a 200-block conversation with one breakpoint at the end, an edit at block 150 loses *everything*, including the 13k system prompt and tools (§J). Add explicit breakpoints (up to 4) after the tools/system prompt and after the documents.
- **Templates that rewrite history.** Qwen3-style templates drop earlier reasoning when a new user message arrives, and gpt-oss drops analysis once a final answer exists. That re-renders the whole previous query from its first assistant turn. In §H (10 queries, 300 reasoning + 100 action + 1,000 observation tokens per step), the token hit rate falls from 97.7% to 94.7% at 5 tool steps per query. That makes per-token input cost **1.27×**, or 1.10× at 20 steps.
  - xAI's documentation names dropped `reasoning_content` as the top cause of misses.
  - Fixes on your own stack:
    - render with reasoning kept, if the template allows it and quality holds;
    - or send token IDs instead of text, which also avoids re-tokenization drift;
    - or strip the reasoning through an in-place splice (Idea 2).
- **Re-serialization.** Key order, tool-schema order and changing timestamps are common causes.
  - Stateful APIs such as OpenAI's `previous_response_id` keep history on the server and so remove client-side serialization drift. I did not verify that they improve hits.

**1f. Tool: `cachediff.py prev.json next.json`.** Give it two consecutive request bodies (Anthropic or OpenAI format). It reports:
- the first block that differs;
- a likely cause (timestamps only, IDs only, JSON key order, lines reordered, reasoning removed, or a real edit, with context);
- how many tokens after that point are unchanged but recomputed;
- the cost multiplier;
- a warning when the 20-block lookback will lose the prefix.

On the test pairs in `examples/`, a one-character change to a tool output at message 4 of 61 gives about an 11% cacheable prefix and costs 11.2× a full hit. A tool schema with its keys reordered gives 0% and costs 12.5×. Token counts are chars/4 estimates.

**Cases and hit rate (§C).** Agent layout: 3k system prompt, 8k tools, 2k memory changing on 10% of turns, 500-token to-do list changing on 50%, 20k documents changing on 2%, 40k conversation, 1k new tokens per turn.

| Layout | Token hit rate |
|---|---|
| Authoring order | 47.1% |
| Best order, conversation last | 67.4% |
| Volatile tail after the conversation | 93.7% |
| + document changes as errata | 95.3% |
| + tail re-sent only when changed | **98.0%** |

- A middle edit, insertion or changed tool output costs only the erratum: about 99.3% that turn for a 500-token erratum in a 74k prompt.
- Reordering a document set that was already seen gives 100%.
- **RAG with a different document set per query (§E):** 2,000 documents of 500 tokens, 5 per query, Zipf popularity with exponent s = 0.8–1.2.
  - Total hit rate: relevance order 55–63%, hash order 57–68%, **popularity order 63–77%**.
  - Counting document tokens only: 20–33% for relevance order versus 34–60% for popularity order.
  - A greedy radix-tree walk (CacheWeaver/RAGBoost style) adds only 0–0.4 points over a static popularity order under i.i.d. Zipf. It should matter more when popularity drifts or topics correlate, which I did not model.

**Quality.** The KV is exactly what the model computes for the prompt it receives. The risks are in what the prompt means:
- stale text stays next to its correction;
- popularity order differs from relevance order ("lost in the middle");
- reasoning kept in history is out of distribution for templates trained to strip it.

Tests, A/B against editing in place, on a real model:
- a needle test where a superseded fact sits next to its erratum;
- SWE-bench resolve rate with errata versus in-place edits, and with reasoning kept versus stripped;
- RAG QA under relevance versus popularity order, with and without an order hint.

**Prior art and what this adds.**
- Already known:
  - Manus and Anthropic advise append-only context with stable content first.
  - *Don't Break the Cache* measures 41–80% cost cuts from excluding dynamic tool results.
  - RAGCache, RAGBoost/ContextPilot and CacheWeaver already reorder documents for reuse.
  - The template and reasoning-stripping trap is documented by xAI and in vLLM practitioner write-ups.
- New here:
  - the odds/size ordering rule, with a counterexample to p/s;
  - the diff-only tail placed after the last breakpoint;
  - the ski-rental compaction threshold;
  - quantified costs of the lookback trap and of reasoning stripping;
  - TTL choice and key sharding as cost levers;
  - a break-diagnosis tool;
  - the finding that a static popularity order captures nearly all of the greedy walk's gain under i.i.d. Zipf.

## Idea 2: Delete and splice KV in place (own stack or provider, approximate)

**Mechanism.** An operation `edit_span(range, replacement)`:
1. drop the span's paged KV blocks;
2. re-rotate the RoPE keys after the span, or leave a gap in position IDs;
3. prefill only the replacement;
4. on sampled requests, compare against exact recomputation of the suffix (the gate from Idea 3).

**Cost.** No extra memory, since freed blocks return to the pool. The rotation is O(suffix) element-wise work.

**Cases.** Clearing old tool results, replacing a tool output, and stripping earlier reasoning (1e) without re-rendering. The hit rate for a replacement is remaining/(remaining + replacement).

**Trace replay (§D).** Step sizes come from 3 small SWE-agent trajectories (41 messages in total, median observation 65 tokens, chars/4). They are resampled into 30- and 80-step sessions, keeping the last 5 observations. Treat this as illustrative: bigger trajectory sets are on Hugging Face and GitHub, which are blocked here.

| Policy | Hit, 30 steps | Input cost, 30 steps | Hit, 80 steps | Input cost, 80 steps |
|---|---|---|---|---|
| Append-only | 94.4% | 1.00× | 97.8% | 1.00× |
| Client elision every step | 69.8% | **1.79×** | 80.1% | 1.30× |
| Client elision every 15 steps | 90.5% | 1.05× | 94.4% | 0.77× |
| **Server splice** | 91.8% | **0.82×** | 95.5% | **0.62×** |

- Eliding old observations on the client every step costs more than not eliding at all, as SWE-agent's own comments warn.
- The splice keeps the saving from deletion without paying for the suffix rewrite. Its hit rate is slightly lower only because the denominator shrinks.

**Quality.** Not exact. Tokens after the deleted span keep what they absorbed from it, and only keys get a position correction (PatchKV). Leyline reports splices that track the full-context baseline on MLA models.

Tests against full recomputation on agent traces:
- KL divergence and top-1 agreement of next-token distributions;
- task success for the gap variant versus the rotation variant;
- a "deleted wrong fact" probe. Where leftover influence would do harm, also append an erratum.

**Prior art.** llama.cpp context shift, StreamingLLM, Leyline, *KV Cache Can Be Editable and Composable*, and KVEraser (which needs a learned editor, so it fails the no-training rule).
- What this adds: billing a splice as a hit, using it to strip reasoning from history, a gate driven by measured deviation, and the cost comparison on traces.

## Idea 3: Content-addressed segment cache with a shadow-calibrated gate (own stack or provider, approximate)

**Mechanism.**
1. Cache each document, tool output or memory unit by content hash, prefilled after the shared system prompt (APE style).
2. When a segment appears at a new position, re-rotate its keys.
3. Fix up cross-segment attention with one of:
   - recompute the ~15% most-deviating tokens (CacheBlend);
   - recompute the first tokens of each chunk (EPIC);
   - apply an offset correction (AgentKVShift, 10–30% refreshed; KVCOMM uses the same offset idea for multi-agent prefill).
4. **Gate (new):** on 1% of traffic, also run exact prefill in shadow. Fit a threshold on a cheap deviation signal so that top-1 agreement over the first 64 generated tokens is ≥99%. Requests above the threshold fall back to the exact path, which still gets its prefix hit.
5. Charge two prices: an exact hit and a cheaper approximate hit.

**Cases.** Reordering, insertions, changed segments, and RAG with a different document set per query.

**Hit rate and cost (§E, §I).**
- 98% of document occurrences had been seen before, so segment coverage is 96% of document tokens. Prefix reuse with popularity order reaches 34–60%.
- Compute cost per document token, counting the 1% shadow:

| Gate fallback rate f | 0% | 10% | 30% | 50% |
|---|---|---|---|---|
| Saving, s = 0.8 | 2.40× | 2.10× | 1.68× | 1.40× |
| Saving, s = 1.2 | 1.60× | 1.51× | 1.35× | 1.22× |

Assumptions: loading a token costs 0.1, a refreshed fraction of 0.15, and a miss costs 1.0. The method stays ahead at any fallback rate, but the gain shrinks quickly. Multi-hop workloads, where fallbacks are common, gain the least.

Published prefill speedups:
- CacheBlend: 2.2–3.3× time to first token;
- EPIC: up to 8×;
- CacheSlide: 3.1–4.3×;
- AgentKVShift: 2–3.5×.

**Storage:** one KV copy per unique segment. That is 320 KiB/token for Llama-3-70B in BF16, 160 KiB in FP8, and about 69 KB for DeepSeek-V3 (MLA).

**Quality.** The papers report results close to full recomputation on single-hop RAG. All methods leave a gap on multi-hop and cross-chunk reasoning (Fusion-RAG; AgentKVShift says so itself).

Tests:
- 2WikiMQA, MuSiQue and LongBench against exact prefill;
- KVShareArena;
- the gate's fallback rate in production, which is the real cost driver according to the table above.

**What this adds.** A gate calibrated in production by shadow sampling against a stated agreement target, an explicit approximate-hit price, and the saving-versus-fallback curve. Running Idea 1's ordering first sends only truly non-prefix tokens down this approximate path.

## Idea 4: Price retention against recompute cost and bandwidth (own stack or provider, exact)

Keep KV in a tier only while expected reuses × recompute cost exceed storage cost × time. Load from a tier only when that is faster than recomputing.

§F assumes Llama-3-70B on 8×H100 at $2 per GPU-hour and 45% utilization.

**Recompute cost:**

| Context length | Recompute speed | Cost per 1M tokens |
|---|---|---|
| 8k | 23.7k tokens/s | $0.19 |
| 32k | 19.6k tokens/s | $0.23 |
| 128k | 11.6k tokens/s | $0.38 |

**Retention break-even (BF16; FP8 doubles these windows):**

| Tier | Keep only if reused within |
|---|---|
| GPU memory (HBM) | 1.4 min |
| CPU memory (DRAM) | 6.9 min |
| NVMe SSD | 2.6 h |

**Bandwidth check.** One NVMe drive loads 21k tokens/s in BF16, which is no faster than recomputing. Four drives (85k tokens/s) or 400 Gb/s RDMA (153k tokens/s) do help. This fits the ~1.2× gain from tiered caching that your earlier run measured on real traces.

**Cost versus price.** Recomputing a token on a 70B-class model costs the provider about $0.19/M. That is below a $3/M model's cached-read price of $0.30/M, so the size of the hit discount is a pricing choice, not a cost fact. Self-hosters should optimize their own compute cost.

**Quality:** no effect, since the KV is exact. This makes near-100% hits affordable for long-tail sessions, but it creates no hits after middle changes.

## What cannot reach ~100% under these constraints

- **Exact hits after an in-place change.** In a causal transformer, the K/V at every layer ≥1 for every later token depend on the changed token. Only layer-0 K/V can be reused exactly, by re-rotation. So an exact method saves at most about 1/L of the suffix work (1/80 ≈ 1.25% for a 70B model). Exact near-100% hits require not editing in place (Idea 1), with the risks to meaning that brings.
- **New document combinations per query.** Exact reuse is capped at 34–60% of document tokens in the replay. Segment reuse reaches ~96%, but only approximately.
- **Multi-hop and cross-chunk reasoning on reused segments.** Every published approximate method leaves a gap, and the savings shrink with the fallback rate (§I).
- **Templates that rewrite history**, on hosted APIs you don't control. An API user can only pass content back in the form the provider caches.
- **Cost.** At 100% hits the floor is reads + writes + output (59/28/13%). Going below it needs fewer tokens read (Ideas 1 and 2), not more hits. Retention (Idea 4) can make 100% uneconomic for sparse reuse.

## What needs a real model

Every quality claim needs a run on a real model, because huggingface.co is blocked here:
- errata semantics and document-order effects;
- keeping reasoning in history;
- splice deviation;
- the segment-reuse gap and the gate threshold.

Until then, these are the papers' own results or untested. The same goes for exact token counts, where chars/4 is used here.

**What was done here:**
- exact arithmetic;
- a brute-force check of the ordering rule;
- a Zipf RAG replay;
- a bootstrap over small real SWE-agent trajectories;
- synthetic tests of `cachediff.py`.

**What was not done or not verified:**
- I did not replay the Mooncake trace. Its hashes are chained to the prefix, so it cannot test non-prefix reuse.
- GPU, storage and DRAM prices are my assumptions.
- Gemini's discount figures come only from secondary sources.
- A blog's figure of 1.7%→92.2% hits on 610 Codex traces in vLLM is unverified.
